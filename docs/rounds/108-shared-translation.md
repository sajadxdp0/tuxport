# M9 之前：同一个程序共用翻译（2026-10-30）

[第二轮普查](70-survey-suites.md)的问题 5：每个进程各一份 Tier 1 的翻译。[上一轮](107-code-density.md)之后，`xargs -P4` 编译 Lua 时四个 cc1 各占 34–40 MB 代码缓存，峰值 155 MB；20 个空闲的 python3 各约 4 MB。手机上 `make -j8` 就是 300 多 MB。

翻译只取决于 pc 和指令字，所以几个地址空间在同样的地址映射着同样的代码时，块对它们都有效。tuxport 没有 ASLR，同一个程序的进程（fork 出来的、exec 了同一个程序的）映射在同样的地址上，可以像一个地址空间里的线程那样共用一个实例。难点是保证一个成员永远执行不到只对另一个成员有效的块。

## 做法

- **按程序组成组**（`mm::CodeGroup`，登记在 Kernel 的 `code_groups` 里）：
  - 线程第一次运行时（`Mm::code_space`），找同一个程序（可执行文件的 inode，与池的键相同）、还开着、映射一致的组，加入它，共用它的 `DbtSpace`。
  - 找不到就和原来一样从池里拿一个实例，所有可执行映射都可信时开一个新组。
  - 每个地址空间仍有自己的 `CodeSpace`，按自己的代码代数作废。
- **成员的可执行映射都得是可信的，而且与组里登记的一致**：
  - 可信的是没写过、有版本的私有文件映射（[第 28 轮](28-spawn-host-cost.md)的版本：宿主 object 的 ctime 和大小），和内容没被改过的 vDSO。vDSO 经由页表读出来和镜像比：fork 出来的子进程的页借自父进程，它自己的宿主内存还是零。
  - 一致是说同一段地址上是同一个版本的同一个文件，地址减去文件偏移也相同。动态链接器先按整个文件的跨度映射，再把后面的段盖上去，同一个库的可执行映射会先长后短；第一版要求起点和长度也相同，cc1 加载第一个库时就离开了组。
  - 没登记过的一致映射登记进来，最多 256 段。
- **每次系统调用之后核对**（`Mm::sync` 里的 `check_code_group`）：
  - 可执行映射有了变化（`insert`、`insert_vma`、mprotect、栈增长、`write_kernel` 写到可执行的映射，比如 gdb 下断点）时才核对，平时只看一个标志。
  - 映射了不可信的可执行内存（JIT、写过的代码）或与登记的不一致的文件的成员离开组：组里还有别人时，它换用自己的翻译，并做一次 shootdown；只剩它自己时组关掉，它留着原来的翻译。 → 留着的翻译里有别的成员（已经退出、离开了的）在登记过的地址上翻译的块，它在那里映射了别的文件，执行到了它们，偶发 SIGILL；现在作废与它的映射对不上的块（M9 之前：共用翻译的组里最后一个成员离开时作废别人留下的块）
  - 离开后它不再加入任何组。
- **离开时换空间**：`Generations` 多了一个空间的代数。线程在循环开头先标记"在执行 guest 代码"、再读代数，与 TLB 的代数是同一个协议。读到变化就退出 guest 状态、取 BKL，换用新的翻译。所以离开之后，它的线程不会再把 JIT 代码之类翻译进组里的实例。
- **第二个成员加入时作废登记范围以外的块**（引擎新接口 `tuxport_dbt_retire_outside`）：开组的那个从池里拿到的实例，可能还有上一个使用者留下的、只对它有效的块（含停放着的）。
- **第一个进程也记下程序文件**（`Machine::spawn`）：原来只有 execve 设 `Mm::exe`，tuxport-run 和 App 直接起的第一个进程没有，池里的翻译键是 0，也开不了组；以写方式打开它的程序文件也不是 ETXTBSY（Linux 上是）。

成员拆掉自己的映射时照常作废，作废的是组里的实例，别的成员只是要重新翻译。离开的成员还没处理的作废记录不落到组里的实例上：那是它自己的变化，别的成员那里的映射没变。

## 结果

| 负载 | 之前（第 107 轮） | 之后 |
|---|---|---|
| 20 个空闲的 python3：代码缓存 | 77.9 MB | 4.4 MB |
| 同上：App 的用量（RssAnon + RssShmem） | 193 MB | 84 MB |
| `xargs -P4` 编译 Lua：代码缓存的峰值 | 155 MB | 53 MB |
| 同上：峰值时的 RssAnon | 160 MB | 107 MB |
| Codex 的界面：App 的用量 | 194 MB | 188 MB |

原生 20 个 python3 的匿名内存合计 59 MB。这几轮下来（第 106 到 108 轮），20 个 python3 的 App 用量从 321 MB 降到 84 MB。Codex 只有两个大进程，共用帮不上忙，少的是池里的实例（20 个 → 9 个）。

计时（`target/mem/ab106.sh`，与第 107 轮的二进制交替 3 轮；`xargs -P4` 交替 2 轮）：

| 负载 | 之前 | 之后 |
|---|---|---|
| shell 起进程（200 次 `ls` 和管道） | 0.23–0.26s | 0.17s |
| `xargs -P4` 编译 Lua 的 33 个文件 / `-P1` | 5.91–5.99s / 15.68–15.69s | 5.11–5.17s / 15.60–15.86s |
| `go build` 冷编译 | 5.82–6.03s | 5.75–5.91s |
| python / gcc / `git status` | 1.33–1.36s / 2.22–2.37s / 0.07–0.09s | 1.35–1.39s / 2.22–2.36s / 0.07–0.08s |
| `node -e 0` 之后 10 次 / Maven / Gradle | 0.43–0.45s / 5.82–5.98s / 1.31–1.44s | 0.42–0.45s / 5.83–5.97s / 1.32–1.37s |

shell 起进程快了约三成：fork 出来的子进程直接加入父进程的组，不用再从池里拿实例、逐块核对。原生是 0.15 秒，现在是原生的 1.13 倍。`-P4` 的几个 cc1 直接用前一个翻译好的代码。

## 测试

- 新的差分测试组 `shared-code`：两个进程经由不同的文件（`files`）、各写各的代码（`jit`）、改写共用的文件（`rewrite`）、exec（`exec`）、按不同顺序 dlopen（`dlopen`）在同一个地址上放不同的代码，两个执行层下都与原生相同。文件写好之后要等 3 秒才可信，用例里等着。
- 新的 rootfs 测试 `processes_of_one_program_share_translations`：一个 shell 起的几个 sleep 在 tuxport-run 里只有一两份代码缓存。
- 单元测试 `code_groups_register_only_consistent_mappings`：哪些映射算一致、有冲突时整个不登记、登记满了。
- 只在 colima 的虚拟机里跑，没上手机。

## 推迟项

- 成员跳到一个只有别的成员映射过、自己没有映射的地址时（野指针、跳进已经 dlclose 的库），执行的是那里的翻译，而不是收到 SIGSEGV。要发现的话每次进入块都得查一次取指的权限。
- 离开组只看可执行映射有没有变：成员拆掉一个库、在同一个地址映射别的库时离开，只拆不映射时不离开（组里登记的还在，之后在那里映射别的东西时离开）。离开之后不再加入，要重新翻译它自己的代码。
- JIT 负载（node、JVM）一映射可写可执行的内存就关掉组：几个 node 进程不共用。它们的 JIT 代码本来就各不相同，不过 node 自己的代码（V8、ICU 这些库）可以共用。→ 已改（M9 之前：有 JIT 代码的进程也共用翻译）：JIT 等不可信的可执行内存是成员私有的，那里的块按成员的标签分开，4 个空闲的 node 的代码缓存 70 → 21 MB
- 文件写好之后两秒内（版本不可信）启动的进程不能共用，它 fork 出来的子进程也不能。刚装好、刚编译好的程序第一次运行时就是这样。
- 并行编译时三四个 cc1 共用一个实例，翻译时在实例的锁上排队，块的链接也是共用的；`-P4` 快了 13%，没有看到锁的争用，线程更多时没量。
