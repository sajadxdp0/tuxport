# M9 之前：V8 和 HotSpot 的寄存器（2026-10-30）

[Go 换一组被占用的寄存器](113-go-registers.md)的推迟项：V8 固定用 x26（根表）、x27（上下文）、x28（指针压缩的基址），HotSpot 固定用 x27（堆基址）、x28（当前线程），正好是 Tier 1 默认占用的几个（§4.2）。这一轮量它们的 JIT 代码，结论是不换：只读不写的寄存器被占用代价很小，默认的一组对 HotSpot 已经是最好的，对 V8 换成 Go 的一组只让 tsc 快 2–4%。

## 怎么量的

上一轮按程序文件反汇编，JIT 生成的代码量不到。这一轮把 `/bench/jvm`、`/bench/dstore` 两个仓库导出成原生的 Alpine 容器，perf 按单调时钟全系统采样（`target/regs/run.sh`），同时记下 JIT 代码的字节：node 用 `--perf-prof` 写的 jitdump，java 用一个 JVMTI 代理（`target/regs/codedump.c`，记下编译好的方法和解释器、桩这些动态生成的代码）。每个样本取那一刻之前最后一次生成在那个地址的代码，文件里的代码按偏移读，再按指令用到的通用寄存器归类（`target/regs/regjit.py`）。用户态的样本 98% 以上对上了指令（匿名内存里的 JIT 代码在 perf 里记在 `/tmp/perf-<pid>.map` 名下）。被占用的寄存器都算上 x18：

| 负载 | JIT 代码占用户态 | 用到被占用寄存器（默认 / Go 的一组） | 写被占用寄存器（默认 / Go 的一组） |
|---|---|---|---|
| `node -e 0` ×20 | 0% | 5.3% / 8.0% | 2.5% / 2.7% |
| node 计算循环和排序 | 54% | 8.2% / 2.3% | 1.9% / 0.7% |
| node 的 Map 和 JSON | 1.4% | 7.1% / 6.0% | 2.4% / 1.8% |
| tsc 5.9 检查 `typescript.d.ts` | 12% | 9.8% / 8.4% | 5.4% / 2.3% |
| prettier 格式化 `lib.es5.d.ts` | 7.0% | 8.2% / 8.6% | 4.2% / 2.3% |
| java 的 Main（`/root/jvm`） | 48% | 6.0% / 10.8% | 1.1% / 2.2% |
| Maven 热构建 | 23% | 6.6% / 12.1% | 1.4% / 2.4% |
| Gradle 热构建 | 20% | 6.9% / 11.8% | 1.5% / 2.4% |
| gcc 编译 `lvm.c`（对照） | — | 5.5% / 9.8% | 2.0% / 2.8% |
| `go build`（对照） | — | 16.1% / 0.7% | 12.0% / 0.4% |

V8 的解释器和内置函数在 node 二进制里，JIT 代码只在计算循环里占大头。Maven、Gradle 七成的时间在 libjvm.so 里，是 JVM 自己的 C++ 代码（JIT 编译器、GC、类加载等）。Go 的一组对 HotSpot 不合适：模板解释器把分派表放在 x21、字节码指针放在 x22（Go 的一组里最常见的被占用指令是分派的 `ldr x9, [x21, w9, uxtw #3]`）。"写"按第一个寄存器操作数是目的来近似，存储、比较、分支除外。

## 按"用到"挑的组合反而更慢

在 x8–x17、x19–x28 里穷举 5 个（`target/regs/choose.py`），能让 node 降到 4% 左右、JVM 降到 2% 左右。实验版引擎（`target/regs/expbuild.sh`，不提交）让 `TUXPORT_DBT_REGS=go` 改用 `REGS_EXP` 给的一组，同一个二进制四种组合交替 3 轮（`target/regs/ab.sh`），单位是秒：

| 负载 | 默认 | (13,15,16,17,27) | (13,15,17,25,28) | (13–17) |
|---|---|---|---|---|
| node 计算循环和排序 | 0.30–0.30 | 0.32–0.34 | 0.33–0.33 | 0.36–0.43 |
| tsc | 2.40–2.49 | 2.41–2.49 | 2.34–2.47 | 2.39–2.62 |
| prettier | 1.04–1.15 | 1.04–1.14 | 1.02–1.25 | 1.04–1.26 |
| Maven 热构建 | 5.68–6.19 | 5.67–5.98 | 5.94–6.42 | 5.78–6.13 |
| Gradle 热构建 | 1.34–1.40 | 1.31–1.32 | 1.34–1.51 | 1.31–1.47 |
| gcc | 2.21–2.38 | 2.14–2.56 | 2.16–2.50 | 2.31–2.49 |

别的负载都在波动范围里，计算循环三组都更慢，前两组"用到"的比例却比默认低（7.6%、6.0% 对 8.2%）。默认的一组里循环最常见的被占用指令是 `ldurb w4, [x26, #-207]`，经由根表读，x26 不变，从 CPU 上下文读它不在依赖链上，乱序执行藏得住；换了之后是 `lsl x13, x12, #32`，x13 是循环里的临时值，写进上下文、紧接着 `cmp x11, x13` 再读出来，压在依赖链上。V8 的 x26–x28、HotSpot 的 x27、x28 都是这种不变的基址。Go 上一轮收益大，是因为 Go 的 x16（栈检查）、x27（汇编器的临时寄存器）不停被写。"写"的比例与实测的快慢一致：计算循环里默认 1.9%，三组依次 5.0%、3.9%、8.1%。

## V8 换 Go 的一组

按写的比例，Go 的一组在 node 的负载上除了启动（2.7% 对 2.5%）都比默认低，tsc、prettier 里写的主要是 V8 的宏汇编器当临时寄存器用的 x16、x17。正式的二进制，tsc、prettier 在默认的一组和 `TUXPORT_DBT_REGS=go` 下交替 8 轮、每轮各跑两次（`target/regs/abts.sh`），中位数：

| 负载 | 墙钟（默认 / Go 的一组） | 用户态 CPU 时间（默认 / Go 的一组） |
|---|---|---|
| tsc 第一次 | 2.51 / 2.42 秒（−3.8%） | 4.74 / 4.72 秒 |
| tsc 第二次 | 2.57 / 2.51 秒（−2.3%） | 4.85 / 4.83 秒 |
| prettier 第一次 | 1.06 / 1.05 秒 | 1.83 / 1.84 秒 |
| prettier 第二次 | 1.07 / 1.05 秒 | 1.81 / 1.81 秒 |

另外交替 5 轮，`node -e 0`、计算循环在两组下相同。只有 tsc 的墙钟快一点，CPU 时间不变，可能是 JS 的主线程快了、后台的编译和 GC 线程（C++ 代码，在 Go 的一组下用到被占用寄存器的更多）慢了，没有分线程量。node 没有 Go 那样的 ELF 注记，要认出 V8 只能看程序的动态符号之类，Electron、deno 这些也要各自认，不值得为这点收益做。

## 推迟项

- V8 的程序用 Go 的一组：tsc 墙钟快 2–4%，别的负载没有变化，要先能在 execve 时认出 V8。
- 只在开发用的虚拟机（大核，乱序执行）上量过。手机的小核（A510、A520）是顺序执行的，从上下文读不变的基址也要实打实地花时间，各组之间的差别可能变大，没上真机（R1）。
