# M9 之前：超级块的实验（2026-10-26）

上一轮的推迟项：块入口、返回、链接合计约占翻译后代码的四分之一。

## 做法

试了两种把执行路径接着翻进同一个块的做法（都用环境变量开关，只做到能量收益的程度，没有处理作废）：

- **调用之后接着翻译返回点**：`bl` 改成跳往块尾的调用桩（压影子返回栈、设 guest 的 x30，再经由链接桩跳往被调函数），宿主的返回地址就是紧跟着的 pc + 4 的翻译，函数返回时直接落在那里，不必先回到落点、再跳往另一个块。
- **无条件前向跳转接着翻译目标**：目标在同一页、块里还放得下时，接着翻译目标处的指令（块的范围仍是连续的一段，跳过的指令也算在里面，核对、作废照样按页）。

## 结果

| 负载（3 轮交替） | 现在 | 前向跳转 | 前向跳转加调用 |
|---|---|---|---|
| gcc 冷编译 / 同一会话第二次 | 2.17–2.21 / 1.95–1.98s | 2.16–2.24 / 1.95–1.99s | 2.18–2.25 / 2.17–2.23s |
| python 启动 5 次加循环 | 1.36–1.40s | 1.37–1.40s | 1.35–1.37s |
| python 循环连跑 3 次 | 2.08–2.14s | 2.05–2.10s | 2.02–2.11s |

只开调用那一项时，python 快约 2%、gcc 不变。块入口和返回的样本主要是返回序列本身（8 条宿主指令）和跳进代码缓存里另一处的开销，少一次落点跳转省不了多少；两项一起时同一会话里第二次编译 gcc 反而变慢（返回点既在调用者的块里、又会被单独翻译成块，代码量变大）。要做成正式的还得在作废块时把块里的每个返回点改成跳往转发桩、翻译模板也要记下它们，收益不值得，没有采用。
