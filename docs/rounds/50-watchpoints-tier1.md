# M9 之前：Tier 1 里的观察点（2026-10-27）

[硬件断点和观察点](44-hw-watchpoints.md)那一轮让有断点或观察点的线程整个用解释器执行，比 Tier 1 慢一个数量级（sha256sum 加 gzip 2 MB：Tier 0 2.8 秒，Tier 1 0.11 秒）。gdb 的 `watch` 最常见的用法是在程序跑了一阵之后等某个变量被改，这段时间全在解释器里。这一轮让有观察点的线程照常用 Tier 1，只把被观察的页上的访问交给解释器（§4.2、§7.6）。

## 做法

- **被观察的页不进 TLB**：Tier 1 的访存先查数据 TLB，命中就直接访问宿主内存，所以只要被观察的页不在 TLB 里，翻译后的代码就不会绕过观察点。C 的填表（`tuxport_tlb_fill`）在页上有观察点时不填对应的一半：读的一半只看读观察点；写的一半在页上有任何观察点时都不填，因为 Tier 1 的原子读改写、独占访问、`dc zva` 也查写的一半。gdb 的 `watch` 是写观察点，被观察的变量所在的页上的读照样在翻译后的代码里。
- **回填交给 Tier 0**：TLB 没命中时翻译后的代码自己按页表填表（回填例程），这里不方便比较观察的范围，所以线程有观察点时回填例程直接失败，像访问出错时一样把这一条指令交给 Tier 0：Tier 0 检查观察点，命中就以 `FaultKind::Watchpoint` 退出（指令没有执行，与 Tier 0 里一样），没命中就执行它、按上面的规则填表，没被观察的页之后照常命中。共用一次检查的一组访存回填失败时原来会记下"这里不再分组"，有观察点时不记（失败不是因为这一组不能共用检查）。
- **何时清空 TLB**：观察的范围变了（跟踪者每次让线程继续都重新设置一遍，没变时不清）就清空线程的 TLB（`CpuState::set_hw_debug`），新被观察的页不会留在里面，不再被观察的页之后重新填进去。
- **硬件断点**仍然整个线程用解释器执行：Tier 1 不在每条指令之前比较 pc（gdb 默认用软件断点，`hbreak` 很少用）。

## 结果

在 gdb 里跑一个先算一阵（1 MB 的数组过 200 遍）、最后写一次全局变量的程序，用 `watch` 等这次写（`target/mem/watch/`）：上一轮 10.8 秒（被观察的线程整个用 Tier 0），这一轮 0.45 秒，不设观察点 0.43 秒（都含 gdb 自己的启动）。最坏的情况是被观察的变量和循环每次都写的数据在同一页（四百万次写都交给 Tier 0）：上一轮 0.60–0.62 秒，这一轮 0.33–0.36 秒，不设观察点 0.22 秒。两个二进制交替各跑三次。没有观察点时回填例程多读一次计数、比较一次，标准基准（shell、git、gcc、python、apk、go build、Maven 和 Gradle 的热构建）都在噪声范围内。

## 测试

引擎测试新增两项（Tier 1 下）：写观察点和读观察点下，被观察的页上的访问交给 Tier 0、命中时停在那条指令上，别的页留在翻译后的代码里，去掉观察点后整页回到翻译后的代码；共用一次检查的一组写栈停在写被观察的槽的那一条；原子加触发读观察点。差分测试的 `gdb` 组和 `ptrace` 组原来在 Tier 1 下也是被观察的线程整个用 Tier 0，现在走新的路径，与原生一致。

## 推迟项

- 有观察点时每次 TLB 没命中都交给 Tier 0 执行一条指令（由它填表），工作集超出数据 TLB（4096 页）的程序比没有观察点时慢；可以在回填例程里比较观察的页，只让被观察的页失败。
- 被观察的页上没被观察的字节，每次写（读观察点时每次访问）都交给 Tier 0。
- 有硬件断点的线程仍然整个用解释器执行。
