# M9："文件"App 按内容认出文本文件（2026-11-03）

[在"文件"App 里浏览](196-documents-read.md)那一轮的推迟项：provider 只按扩展名猜类型，没有扩展名的文本文件（`/etc/profile`、脚本、`Makefile`）和 `.bashrc` 这样的点文件（点后面的 `bashrc` 不是认识的扩展名）都是 `application/octet-stream`，"文件"App 里点开没有 App 能接，只能复制出去。[家目录可写](197-documents-write.md)之后，用 Android 上的编辑器改点文件和脚本正是常见的用法。

## 做法

- 先照旧按扩展名猜（`MimeTypeMap`）。猜不出的普通文件（没有扩展名、扩展名不认识）一起交给 `Native.browseSniff`，一次打开仓库看完：一次列目录、一次搜索、一个文档各一次，不是每个文件一次。
- 内核层的 `browse::looks_like_text` 打开 object（符号链接照样跟随），读开头 4 KB：没有 NUL、是合法的 UTF-8（没读到文件末尾时最后一个字符可以被截断）就算文本，空文件也算。只看 NUL 是 git 判断二进制文件的做法；再要求 UTF-8，免得把压缩过的数据当成文本。是文本就给 `text/plain`，编辑器都接这个类型。
- 一次最多看 1000 个文件，之后的照旧是 `application/octet-stream`：每个都要在宿主上打开、读一次。

开销：模拟器上列一个有 1000 个文件的目录，没有扩展名（每个都要读开头）的 48.9–68.0 ms，`.txt`（按扩展名就知道）的 46.5–56.0 ms，相差在波动之内。

## 测试

- 内核层新增 `text_is_told_by_content`：各种算和不算文本的文件，包括开头 4 KB 处正好截断一个汉字的、整个文件只有半个字符的。
- 仪器测试 `documentsShowTheHomeDirectory` 加上点文件、带 NUL 的文件和指向文本的链接，列目录、查单个文档时的类型都对；仪器测试通过。

## 推迟项

- 只区分"文本"和"不知道"：脚本不按 `#!` 给 `text/x-shellscript`，图片、压缩包这类没有扩展名的不按魔数认。
- Latin-1、GBK 这些别的编码的文本不算文本。
- 结果不缓存：每次列目录都重新读。
