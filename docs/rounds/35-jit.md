# M9 之前：JIT 负载（2026-10-26）

开发类负载里差距最大的是 JVM：Maven 离线打包一个小项目 6.7 秒，原生 1.7 秒。`--stats` 显示每次构建要翻译 73 万个块（22 万个从模板拷贝）、作废 31 万个，Tier 0 退出 17 万次、系统调用 48 万次。按线程剖析（宿主线程名是 `guest-<tid>`，在 guest 里读 `/proc/*/task/*/comm` 对上 Java 线程名）：7.3 秒里一共用了 19.4 CPU 秒，主线程 5.6 秒，C2、C1 编译线程合计约 12 秒；主线程里 libjvm 的 C++ 代码占 37%，Java 代码（模板解释器和 JIT 生成的代码）24%，翻译相关约 15%。

## 时间花在哪里

- **系统调用**：48 万次里 38.5 万次是 `clock_gettime(CLOCK_MONOTONIC)`（`System.nanoTime`），vDSO 的时间函数还只是 svc 存根（§7.2）。量了一下每次约 130 纳秒（原生 20 纳秒），一次构建多花约 40 毫秒，不值得做 vDSO 的快速路径。
- **Tier 0 退出**：8 万次是 `dsb ish`（HotSpot 每改一处代码就 `ic ivau`、dsb 一次，Tier 1 遇到记着页的 dsb 就退出、交给内核层作废翻译），7.9 万次是读写 FPCR、FPSR（合计约 20 毫秒，没有改）。
- **作废**：临时记下每次作废的范围，9.1 万次全是整页的，平均每次作废 3.4 个块：JIT 改写一处代码只 `ic ivau` 一两行，同一页里别的方法的块也一起作废、重新翻译了。

## 做法

- **按内容作废**（§4.2 的"失效"）：作废范围里的块只有 guest 指令字和现在不同的才作废。翻译只取决于 pc 和指令字（字面量也是运行时才读）；拆掉映射、去掉执行权限之后这一页找不到可执行的映射，照样全部作废。停放的块不用管，恢复时本来就要核对。
- **dsb、isb 时就地作废**：Tier 1 记下的页由分发器直接按内容作废，不退出到内核层（原来要取 BKL、记日志、回来再作废）。翻译由地址空间里的线程共用，作废块的入口改写之后，别的线程下次进入就会看到。
- **大实例不挤掉池里别的翻译**：按内容作废之后，一次 `java C.java` 留下的翻译作废的块少了，块数不再超过放回池里的上限（13 万）而被留下；它有 46 MB（87% 在 libjvm 这些文件映射里，下一个 JVM 用得上），连同 node 的 17 MB 超出了池里 64 MB 的上限，把 node 的挤掉了：startab 里接着跑的 node 计算从 0.22 秒慢到 0.28–0.32 秒。现在超过池里一半的实例只在不挤掉别人时保留。

## 结果

两次 Maven：翻译的块 146 万 → 65 万（从模板拷贝的 43 万 → 1.8 万），作废的块 62.5 万 → 5.5 万，链接退出 194 万 → 94 万；主线程的 CPU 时间 5.6 → 5.0 秒，全部线程 19.4 → 18.1 秒。

| 负载（3 轮交替） | 原生 | HEAD | 之后 |
|---|---|---|---|
| Maven 离线打包 | 1.7s | 6.64–6.78s | 6.14–6.26s |
| Gradle 热构建 | 0.42s | 1.51–1.57s | 1.42–1.47s（一次 1.54） |
| `java C.java`（源文件启动器，编译加运行） | — | 1.33–1.35s | 1.26–1.27s |
| node 计算、启动，python 启动，`java -version` | | | 不变 |

node（V8）这边没有这个问题：一次计算负载只作废一两百个块，耗时与原生相同。剩下的主要是 libjvm、JIT 代码本身在翻译后执行的开销。

## 测试

引擎测试新增"作废范围里内容没变的块保留"；差分测试的 java、node、go 组都用到 JIT。

## 推迟项

- FPCR、FPSR 的读写仍交给 Tier 0（Maven 一次 7.9 万次，约 20 毫秒）。guest 的 FP 状态在翻译后的代码里本来就在宿主寄存器里，可以原样执行，但要照着 Tier 0 对各个位的处理来做。
- vDSO 的时间函数仍是 svc 存根（§7.2）：每次 130 纳秒，Maven 一次构建 38 万次。→ 读时钟的系统调用不再取 BKL，单个进程每次 127 → 89 纳秒（M9 之前：拆 BKL）；vDSO 仍是 svc 存根
