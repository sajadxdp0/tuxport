# M9 之前：Go 换一组被占用的寄存器（2026-10-30）

[多线程共用翻译和定向唤醒](24-shared-translation.md)的推迟项：Tier 1 占用宿主的 x16、x17、x26–x28（和不碰的 x18），guest 引用这几个寄存器的指令要先从 CPU 上下文读、执行完再写回（§4.2）。Go 的编译器正好固定用它们：x28 是当前的 goroutine（g），x27 是汇编器的临时寄存器，x26 是闭包的上下文，函数序言的栈检查从 g 读栈界限放进 x16。这一轮让 Go 的程序改占另一组寄存器，`go build` 快 3–5%。

## 先量了一下

原生的 `go build` 用 perf 按时间采样，按每个样本所在的指令用到哪些寄存器归类（`target/mem/regmix.py`，反汇编程序文件）。一条指令可能用到几个寄存器，所以各列相加会多算：

| 程序 | 用到 x16、x17、x18、x26–x28 的指令 | x16 / x27 / x28 | x19–x25 各自 | 其中 x21–x25 相加 |
|---|---|---|---|---|
| compile | 15.5% | 8.1% / 6.3% / 7.4% | 0.1–0.4% | 0.7% |
| go | 12.1% | 5.1% / 6.4% / 5.6% | 0–0.2% | 0.4% |
| gcc 的 cc1（对照） | 5.2% | | | |

Go 的寄存器分配从低号用起，x19–x25 几乎用不到。微基准（`target/mem/stolen2.c`）里同样的循环体，一个用 x16、x26–x28 写成 Go 函数序言的样子，一个换成 x19–x25：

| 循环 | 默认的一组 | Go 的一组 | 原生 |
|---|---|---|---|
| 用 x16、x26–x28 | 3.35–3.37 ns/轮 | 1.29–1.32 | 1.21 |
| 用 x19–x25 | 1.29–1.30 | 3.33–3.34 | 1.20 |

一轮有 6 条指令用到被占用的寄存器，每条多约 0.35 ns（1 个周期左右）。被占用的寄存器带着循环里每轮都要用的值时更贵：原来的 `stolen.c` 把循环计数和累加值放在 x21、x22，在 Go 的一组里它们每轮都要存进上下文再读出来，一轮 4.4–5.0 ns。

## 做法

见 §4.2。

- 寄存器分配在创建 Tier 1 实例时选定（`tuxport_dbt_new` 的 `regs`）：默认的一组 x28 指向 CPU 上下文、x16、x17、x27 是临时寄存器、x26 放 SP；Go 的一组 x25 指向上下文、x21–x23 是临时寄存器、x24 放 SP，guest 的 x21–x25 和 x18 存放在上下文里，x16、x17、x26–x28 放在同号的宿主寄存器里。两组都不碰 x18。
- 翻译器里这几个寄存器的名字改为取实例的那一组，进入、退出例程按它生成：放在同号寄存器里的 guest 寄存器相邻的两个用一条 ldp/stp 读写。默认的一组生成的代码和原来逐字相同。翻译模板按寄存器分配区分版本；池里的实例要程序和寄存器分配都相同才拿回保留的翻译，空的实例换一组时重新生成例程。
- 内核层在 execve 时看程序的 `PT_NOTE`：有 Go 的链接器写的 build ID 注记（`.note.go.buildid`，名字是 "Go"，类型 4）就用 Go 的一组。外部链接的 Go 程序（Alpine 的 go 链接了 musl）也有这个注记。fork 出来的进程沿用，exec 时重新选。
- 环境变量 `TUXPORT_DBT_REGS`（`go` 或 `default`）让所有程序都用同一组，用来测试：差分测试、LTP 用它让 C、Python、Java、Node 的代码也在 Go 的一组下跑一遍。`scripts/dev`、`scripts/difftest` 把它带进容器。

同一个进程里的 C 代码（ld-musl、cgo 调用的库）用 x19–x25 多，在 Go 的一组下更慢：busybox `ls` 静态翻译时要改写的指令从 8.2% 变成 12.2%。不过 Go 的程序里这部分很少运行。

## 结果

同一个二进制，`TUXPORT_DBT_REGS=default` 和不设（Go 的程序用 Go 的一组）交替各 3 轮（`target/mem/ab113.sh`、`ab113cpu.sh`）：

| 负载 | 默认的一组 | Go 的一组 |
|---|---|---|
| `go build` 冷编译 | 5.85–6.21 秒 | 5.67–5.76 秒 |
| 计算型的 Go 程序（map、排序、sha256、接口调用，`target/mem/gocpu`） | 1.76–1.82 秒 | 1.72–1.74 秒 |
| `gofmt -l` 扫 runtime 和 cmd/compile 的源码 | 1.29–1.32 秒 | 1.27–1.29 秒 |

原生的 `go build` 热缓存时 2.1–2.3 秒，现在约 2.6 倍（默认的一组约 2.7 倍）。收益比原来估计的 8% 少。那个估计是拿微基准里每次引用多出的约 1 个周期乘以引用的次数，没算乱序执行能和别的指令重叠掉的部分。`go build` 还有不少时间不在 guest 代码里：起进程、文件操作、BKL。

## 测试

- lockstep 的 Tier 1 两组各跑一遍，和硬件、Tier 0 逐项比对，都一致。
- 引擎的单元测试 `both_register_sets_run_the_same_code`：两组交替运行用到全部通用寄存器的同一段代码，模板、池里空的实例在两组之间来回，以及哪些指令原样拷贝、哪些改写。内核层的 `go_programs_get_their_own_tier1_registers` 测试认不认 Go 注记。
- 差分测试、LTP 在 `TUXPORT_DBT_REGS=go` 下也跑了一遍，与默认的一组结果相同。

## 推迟项

- 别的运行时也固定占着几个寄存器：V8 的 x26（根表）、x27（上下文）、x28（指针压缩的基址），HotSpot 的 x27（堆基址）、x28（当前线程）。但它们的解释器又用到 x19–x25，Go 的一组未必合适。这些代码多半是 JIT 生成的，不在程序文件里，这一轮按文件反汇编的统计方法量不了，要先从 perf 的 JIT 映射里取到指令再看。→ 量过（M9 之前：V8 和 HotSpot 的寄存器）：它们固定用的多是只读的基址，被占用代价小，默认的一组对 HotSpot 已经最好；V8 换 Go 的一组只让 tsc 快 2–4%，要认出 V8 的程序，没做
- cgo 用得多的 Go 程序里 C 代码在 Go 的一组下更慢，没有量。
