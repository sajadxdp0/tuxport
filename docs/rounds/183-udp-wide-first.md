# M9 之前：新命名空间里没绑定的 UDP socket 先发命名空间里、再发外面（2026-11-02）

[上一轮](182-outer-prerouting.md)的推迟项。容器里一个没绑定的 UDP socket：

- 先发往外面、再发往命名空间里的地址：两边都有回答，与原生一样。
- 先发往命名空间里的地址（网关、别的容器、自己的 127.0.0.1）：之后再发往外面是 EINVAL，原生两边都有回答。

## 原因

新命名空间里的 socket 是宿主 socket，地址在系统调用的边界上换算（[网络命名空间](122-net-namespaces.md)、[经由虚拟网卡的连接](171-netmap.md)）：

- 发往命名空间里的地址时，没绑定的 socket 先绑到这个命名空间在宿主上的回环地址 127.a.b.1，对方按它认出来源。
- 发往外面（经由默认路由交给宿主网络）的不能这样绑，绑了就出不去。宿主替它绑通配地址（`Socket::wide`），之后发往命名空间里的地址时用 `IP_PKTINFO` 把源地址指定成 127.a.b.1。显式绑了通配地址、端口 0 的 socket 也是这样。

第一个数据报发往命名空间里时，绑的是回环地址，宿主 socket 定在了那里。再发往外面，宿主不让回环地址出去，就是 EINVAL。

## 影响到谁

上一轮的推迟项里说 DNS 的解析器会碰到，实测不是这样：

- musl 的 `res_msend` 先 `bind` 了通配地址、端口 0，再用这个 socket 问所有的服务器。在 tuxport 里它本来就是 wide 的，resolv.conf 里先写网关、再写外面的服务器，第 179 轮的二进制也解析得出来（用 strace 看过调用）。
- Node 的 dgram、Go、Java 发送之前也先绑定。
- glibc 的解析器给每个服务器开一个 socket，再 connect。

碰到这个问题的是不先 bind 就 sendto 的程序，比如 Python 里直接 `sendto` 的 socket。

## 做法

新命名空间里没绑定的 UDP socket，第一次 sendto 发往命名空间里的地址时，也让宿主绑通配地址、按包指定源地址，与先发往外面时一样。这样先发哪个都一样，也与原生一样：原生没绑定的 socket 第一次发送时自动绑的就是通配地址。

两种情形不变：

- 发给自己的虚拟地址：照旧绑 127.a.b.254，对方的回答按登记的端口送回那里（第 171 轮的 `self_udp`）。
- connect：只连一个对端，照旧绑回环地址。

## 测试

- `netmap` 差分测试组新增一节：没绑定的 UDP socket 按三种顺序发往命名空间里和外面。"外面"一开始用的是外层 eth0 的地址：宿主上从回环地址发往本机地址是允许的，改回原来的写法也通过，所以换成了外层命名空间的默认网关。
- 手动：A 里一个 socket 先问外层通配地址上的服务端、再问 8.8.8.8，两边都有回答（改之前问 8.8.8.8 是 EINVAL）。

## 推迟项

- connect 的 UDP socket 先连命名空间里的地址（绑了回环地址），之后再 connect 到外面、或者带地址 sendto 到外面，还是出不去（EINVAL，原生重新 connect 之后能发，`target/origdst/reconnect.sh`）。只连一个对端的用法碰不到。
