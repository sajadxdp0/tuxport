# M9 之前：锁和宿主 socket 只叫醒等它们的线程（2026-10-27）

[按对象唤醒](49-targeted-wakeups.md)之后，还有几处修改请求整个文件类的通道：解锁（flock、fcntl 的记录锁和 OFD 锁）、关闭加过锁的文件、持着记录锁的进程退出、f_pos 锁放开、关闭宿主 socket、netlink 和 DNS 存根的回答、`F_SETPIPE_SZ`。poll、epoll 的等待者都听这个通道，每一处都把系统里停在 poll、epoll 里的线程叫醒一遍；阻塞在宿主 socket 上的 recv、send、accept、connect 用的是听所有通道、不限对象的等待，连每一次管道、PTY 的读写都会叫醒它们。量下来（`target/herd/sockherd.c`）：8 个进程空等，各自用 epoll 等一个没人碰的 eventfd（"epoll"），或者阻塞在一个没有数据的 TCP 连接的 recv 里（"recv"），主进程各做 2000 次下面的操作，每次操作的微秒数和空等的进程被叫醒的次数（之前、之后各两次）：

| 操作 | 原生 | 之前 | 之后 |
|---|---|---|---|
| epoll：TCP 建立连接、接受、两端关闭 | 19.3 | 45–53（每次叫醒 8.8–10.9 次） | 14.0–15.9（0 次） |
| epoll：flock 加锁、解锁 | 0.6 | 10.0–10.9（3.2–3.9 次） | 0.2（0 次） |
| epoll：fcntl 加锁、解锁 | 0.6 | 15.8–18.5（5.4–6.9 次） | 0.3（0 次） |
| epoll：getifaddrs（netlink） | 11.9 | 87–89（10.3 次） | 44–45（0 次） |
| recv：TCP 建立连接、接受、两端关闭 | 17.8 | 48–51（9.1–9.6 次） | 14.9–15.6（0 次） |
| recv：管道写 1 字节再读出 | 0.4 | 6.7–6.9（1.7–1.9 次） | 0.3（0 次） |

原生的空等进程都没被叫醒过。flock 比原生快，是因为 tuxport 的 flock 在进程内处理，不经过宿主。测量程序最初用另一个进程接受连接，它跟不上时 listen 的队列满了，丢掉的 SYN 要 1 秒之后才重传，TCP 那一项时而 20 微秒、时而 530 微秒，与唤醒无关，后来改成主进程自己接受。

## 做法

- **锁的通道**（`wake::LOCK`）：flock、记录锁和 OFD 锁、租约、打开文件的位置锁（f_pos_lock）放开或者变了，只请求这个通道。等这些锁的线程只听它：F_SETLKW、阻塞的 flock、等租约被打破的 open、等位置锁的读写和 sendfile。F_SETLKW、flock 和租约原来用的是听所有通道、不限对象的等待，任何修改都会叫醒它们。关闭加过 flock、OFD 锁、租约的文件，以及进程退出时加过记录锁的 fd 表，也只请求锁的通道。租约的设置、放弃原来请求所有通道。
- **flock 转换锁的类型时叫醒等锁的一方**（bug）：同一个打开文件从排他锁降成共享锁时，等共享锁的进程原来不会被叫醒，只能等别的修改顺带叫醒它；没有别的修改时，它一直等下去。Linux 转换时先放开原来的锁（`flock_lock_inode`），等着的一方会被叫醒。现在转换时也请求锁的通道。
- **宿主 socket 是唤醒对象**：poll、epoll 登记关注的宿主 socket 和 netlink socket 自己（`net::wake_objects`）。下面几种修改只请求这个 socket：
  - 关闭宿主 socket。在 poll、epoll 里等它的线程，它的宿主 poll 还拿着宿主 fd，要叫醒它放手，宿主 socket 才真正关闭，对方才收到 FIN。
  - DNS 存根和 netlink 的回答。
  阻塞的 recv、send、accept、connect 只登记自己的 socket，加上等它的宿主 fd，不再被别的文件上的修改叫醒。
- **`F_SETPIPE_SZ`** 只请求这个管道：写满了的写端、等可写的 poll 在等它，与 Linux 改大管道时叫醒写端一样。
- 仍请求整个文件类通道的只剩两处：关闭 POSIX 消息队列，以及有 `O_ASYNC` 的文件时信号驱动的 I/O 要重新检查。

## 结果

见上表。标准基准都在噪声范围内，这些负载里没有空等着的 poll、epoll 进程。

## 测试

差分测试 `wakeups` 的空闲部分加了两个空等的进程（阻塞在 TCP 连接的 read 里、用 epoll 等 TCP 连接），别的进程的动作加了 TCP 连接、getifaddrs、各种锁、持着记录锁退出、租约和 `F_SETPIPE_SZ`；叫醒部分加了 13 项：各种锁的持有者解锁、降级、关闭文件、退出，租约被放弃，TCP 的 read、accept 和另一个线程关掉连接，netlink 的回答，`F_SETPIPE_SZ` 改大管道。变异检验里阻塞的 netlink recv 不登记自己的 socket 时测不出来：不带对象列表的文件类等待者会被任何对象上的修改叫醒，登记对象的作用是不被别的对象叫醒，宿主 socket 的这一点由空闲的 TCP read 检查。

## 推迟项

- 关闭 POSIX 消息队列、有 `O_ASYNC` 的文件时信号驱动的 I/O 仍请求整个文件类的通道，叫醒所有 poll、epoll 的等待者。→ 已改：消息队列按对象唤醒，信号驱动的 I/O 只叫醒定时器线程（M9 之前：消息队列和信号驱动的 I/O 不再叫醒所有人）
- `tuxport-run` 交给 guest 的宿主 stdio（`FileKind::Host`）上的阻塞读写仍用听所有通道、不限对象的等待。App 里没有这种文件。→ 已改：阻塞的读只等宿主 fd，写本来就不经过等待机制（M9 之前：宿主 stdio 上的阻塞读只等宿主 fd）
