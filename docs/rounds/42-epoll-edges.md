# M9 之前：epoll 的边沿（2026-10-27）

评估内核兼容性还剩哪些值得做时实测发现，[M8](10-m8.md) 起 `EPOLLET` 的近似会让 tokio 写的程序卡住：`uv pip install --offline` 在 tuxport 里一直不结束，原生 0 秒。卡住时三个线程都在睡，uv 的 eventfd 以 `EPOLLET | EPOLLIN | EPOLLRDHUP` 关注，计数是 2：写过两次、一次也没有读。mio（tokio 的底层）的唤醒器在 epoll 上从来不读走 eventfd 的计数，靠的是 Linux 每次写都让边沿触发的关注再报告一次；原来的近似只在某一位从未就绪变成就绪、或者程序用完数据时才触发，第二次唤醒就丢了。一个小程序对照下来，eventfd、管道、AF_UNIX、TCP 都是这样：已经可读、没有读完时又来了数据，Linux 每次都报告，tuxport 不报告。这一轮按 Linux 唤醒等待队列的时机重做 `EPOLLET`，顺带让水平触发的 `EPOLLEXCLUSIVE` 也只报告给一个 epoll（§10）。

## 做法

- **数据代数**（`syscall::poll` 的 `arrivals`）：进程内的对象每来一次事件记一次，与 Linux 唤醒等待队列的地方对应：管道的写入，AF_UNIX 的消息和监听 socket 上新的连接，eventfd 的写（读的一方）和读（写的一方），timerfd 到期，PTY 的输入（从设备读的）和输出（主设备读的，包括回显），inotify 排进队列的事件，挂起的信号（signalfd；已经挂起的标准信号再产生时不算，与 Linux 一样），消息队列的发送和接收，netlink 和 DNS 存根的回答。AF_UNIX 的发送方也按 Linux 的 `unix_write_space`：对方读走数据之后仍然可写就记一次。边沿触发的关注在某一位从未就绪变成就绪，或者那个方向的代数变了时触发，触发时报告当前全部就绪的位；程序用完数据（EAGAIN、没有读写满）时作废上次报告的位，这一条照旧保留。
- **宿主 socket**：数据不经过内核层，宿主 poll 只能看到现在就不就绪。有边沿触发或者独占的关注时，给这个打开文件建一个只关注那个宿主 fd 的、边沿触发的宿主 epoll（`fd::HostEdges`，HAL 的 `Edges`），宿主每来一次数据它就可读一次，取走事件时按读、写方向计数。检查就绪时它和宿主 socket 放在同一次宿主 poll 里，可读时才去取，所以平时每次检查不多一次系统调用。建不了的（宿主 stdio 是普通文件，宿主 epoll 不收）仍然只看程序有没有用完数据。
- **等待**：边沿触发的关注不等报告过、仍然就绪的位（否则宿主 poll 立刻返回，变成忙等），改为把 `HostEdges` 的宿主 epoll 放进等待的宿主 poll，等新到的数据。进程内的对象来了数据时，管道原来只在空着时叫醒（读端只在空着时等），现在不空时也叫醒边沿触发、少等了事件的 epoll_wait（`Kernel::edge_waiters`）；别的对象本来每次都叫醒。
- **`EPOLLEXCLUSIVE`**：原来只有边沿触发的独占关注一个边沿报告给一个 epoll，水平触发的照样报告给所有 epoll：几个进程各用一个 epoll 等同一个监听 socket（nginx 的做法），来一个连接三个进程都从 epoll_wait 返回，原生只有一个。现在打开文件记着报告过的边沿（数据代数）和报告它的 epoll：水平触发的关注由那个 epoll 接着报告，别的 epoll 等下一个边沿（新的数据、新的连接，或者数据被用完之后再来）。等待的线程仍然都会被叫醒（poll、epoll 的等待者被所有文件类的修改叫醒，§6），没轮到的在内核里重新检查之后接着睡，不回到用户态。
- **信号驱动的 I/O**（`O_ASYNC`）也用同一个数据代数：已经可读时又来了数据也发信号，与 Linux 每来一次数据都 `kill_fasync` 一样。

## 结果

Go 的 HTTP 回环（`target/mem/epoll/httpbench.go`，netpoller 全用边沿触发；上一轮的二进制和这一轮的交替跑三次）：keep-alive 的请求每次 84–87 微秒，两边一样；每次新建连接 201–206 对 209–216 微秒，多 8 微秒左右（4%）：连接两端的 socket 各建一个宿主 epoll（创建、登记、关闭三次系统调用）。

## 测试

新的差分测试 `epoll`：15 种对象各 poke 两次、中间不读，看边沿触发的关注报告几次；mio 的唤醒器（另一个线程写 eventfd、从不读）；三个进程以水平触发的 `EPOLLEXCLUSIVE` 等同一个监听 socket；uv 离线安装一个包（`uv` 加进了差分测试的软件包）。inotify 那一项开头要先删掉目录：仓库里 `/tmp` 留着上一次运行建的文件，`O_CREAT` 不再产生事件（变异检验时发现的）。单元测试新增每次来数据都再触发、独占的关注一个边沿只报告给一个 epoll。

## 推迟项

- 管道、PTY 的写方向仍按"变成可写"和"写满之后用完"判断，读走数据不让写的一方再触发（Linux 的管道只在原来是满的时候叫醒写端，相差不大）。
- 嵌套的 epoll：里面的 epoll 又有新的就绪事件时，外面的边沿触发的关注不会再触发（Linux 会）。→ 已补上（M9 之前：嵌套 epoll 的边沿）
- 每个有边沿触发关注的宿主 socket 多占一个宿主 fd（Go 的 netpoller 给每个 socket 都加边沿触发的关注），连接很多时宿主的 fd 用量翻倍。
- `EPOLLEXCLUSIVE` 只是只报告给一个 epoll，等待的线程仍然都被叫醒。→ 已补上（M9 之前：独占的唤醒）：独占关注的文件上来了新的边沿只叫醒一个等待者
