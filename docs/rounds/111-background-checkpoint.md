# M9 之前：检查点挪到后台（2026-10-30）

[多线程共用翻译和定向唤醒](24-shared-translation.md)的推迟项：SQLite 的自动检查点（WAL 攒到 1000 页时把它写回数据库文件，fsync 两次）在提交的连接里做，提交多半持着 BKL（推迟到点的提交在定时器线程里）。虚拟机的盘 fsync 很快；手机上的 UFS、f2fs 一次 fsync 常常要几毫秒到几十毫秒，这期间要进内核的 guest 线程（包括往终端输出的）都要等。仓库用的是 WAL 加 `synchronous=NORMAL`，平时的提交不 fsync，检查点是唯一 fsync 的地方。

## 量了一下

给 COMMIT 计时（临时插桩 `target/mem/openinstr.py`）：`tar x` 解包 Python 标准库再删掉，连做 5 次（6300 个文件，0.46 秒），84 次提交里有一次带着检查点，持锁 8.4 ms，其余都在 0.1 ms 左右；`go build`、gcc 编译 Lua 一次也没碰上（WAL 没写满）。所以是新建、删除文件多的负载（解包、`npm install`、`git clone`、`apt install`）里每隔几千个文件一次的停顿。

## 做法

见 §8.1。

- 注册 `sqlite3_wal_hook`（代替 SQLite 默认的自动检查点，它也是这个钩子）：每次提交之后由提交的线程调用，报告 WAL 里现在有几页。比上一次请求时多出 1000 页，就请仓库的后台线程（原来只删 object 的那个）做检查点。后台线程用自己的连接做 PASSIVE 检查点：不等读者，也不挡写者。
- 第一版只有这一条，单元测试里 WAL 一直变长：WAL 只有在全部写回之后开始的写事务里才从头再用，后台检查点进行期间又有提交时总差最后几帧，而且一阵写入结束时剩下的几百页没人再写回。所以又加了两条：
  - WAL 长过 1000 页、还有没写回的帧时，后台线程等写入停下 100 毫秒，再写回一次，下一个写事务就让 WAL 从头再用。零星的小写入（shell 的历史记录这类）WAL 长不到这么多，不会多出 fsync。
  - 一直有提交、后台怎么也追不上时，WAL 长到 1 万页由提交的线程就地补一次检查点。这时大部分帧后台已经写回，补的只是最后一千页以内的。
- WAL 从头再用时截短到 8 MB（`journal_size_limit`），不长期占着连续写入时长出来的空间。
- 后台线程没起来时不注册钩子，保留 SQLite 自己的自动检查点。

## 结果

同样的 5 次解包，持锁的提交最长 0.5–0.6 ms，合计 2.8–3.0 ms（原来最长 8.4 ms，合计 11.3 ms）。虚拟机里墙钟没有变化（与上一个提交的二进制交替 4 轮：解包 5 次 0.37–0.38 对 0.37–0.39 秒，复制再删除 Python 标准库 3 次都是 0.16–0.17 秒，新建再删除 2000 个空文件都是 0.04–0.05 秒）：这几项是单线程的，fsync 又快，检查点在哪个线程做总时间都差不多。省下的是持着 BKL 的停顿，到手机上 fsync 慢的时候才显出来。

虚拟机里连续写入时后台大多赶得上：单元测试的第一版不暂停后台线程、连续提交 2000 次，WAL 最长只到 2018 页就从头再用了，到不了就地补的 1 万页。

## 测试

- 单元测试 `checkpoints_run_in_the_background`：检查点由后台做，写入停下之后后台补写回、WAL 从头再用，后台暂停时 WAL 到 1 万页就地补上。
- 推送之后 CI 上这个测试失败了：第一版等的是"后台做完第二次检查点"，机器慢时第二次可能写不回最后几次提交，第一次已经全部写回时又等不来第二次。改成等后台把 WAL 全部写回，虚拟机里另加 4 个忙循环也都通过。

## 推迟项

- 一直在写、后台追不上时，每 1 万页仍有一次检查点持着 BKL，只是补的帧少；虚拟机里没碰上过。
- 没在手机上量 fsync 的时间和这一轮的效果。
