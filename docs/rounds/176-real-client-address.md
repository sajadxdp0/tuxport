# M9 之前：从外面转发进来的连接带上真实的客户端地址（2026-11-01）

[第 173 轮](173-port-forwarding.md)的推迟项。从 tuxport 外面连到发布的端口时，宿主上的转发线程替容器接受连接，再连过去，连接时绑的是网关在宿主上的地址，所以容器看到的来源总是网关（与 docker-proxy 一样）。Linux 上外面的设备连发布的端口走的是 DNAT，容器看到的是客户端真实的地址：访问日志、按 IP 的限流、白名单都按它算。

## 做法

- **按连接分地址**（`core/kernel/src/forward.rs`）：
  - 宿主上 127.254.0.0/16 留给从外面转发进来的连接；新的网络命名空间分宿主地址段时不再取 127.254（原来只跳过开机时的命名空间用的 127.255）。
  - 转发线程接受的连接，客户端是 IPv4、不是回环地址时（别的设备；IPv4 映射的 IPv6 地址也算），从这一段里分一个地址，绑上它和客户端原来的端口（绑不上这个端口就让宿主选），再连容器。
  - 登记 (这个地址 → 客户端的地址、端口、绑上的宿主端口)，连接结束时去掉。登记表在进程里一份，转发线程写、内核层读。
- **换回真实地址**（`netns::from_host`）：任何命名空间里看到的对端是 127.254.x.y、端口也对得上时，换成客户端的地址和端口。所以容器里 accept、getpeername、`/proc/net/tcp` 报告的都是它。低端口映射不换这一段的端口。
- **回环地址的客户端照旧**：手机上别的 App、浏览器开 localhost 连进来时，照旧绑网关的地址。Linux 上从本机连发布的端口时 netavark 做 masquerade、docker 经由 docker-proxy，容器看到的也是网关。
- **UDP 的转发也照旧**：容器回给真实地址的数据报，要经由转发 socket 才回得去，地址映射里没有这个方向。

## 测试

- 单元测试：`forward` 测外面来的连接绑的地址、端口和登记，`netns` 测换回登记的客户端地址。
- 实测：开发容器里后台起 tuxport，从开发容器的 eth0 地址（不是回环）连 podman 发布的端口，容器里看到的对端是客户端的地址和端口；原来是网关。
- 只跑单元测试的变异检查要先在容器里 touch 源文件，不然 cargo 沿用上一个变异时编的东西。

## 推迟项

- 只有 TCP、IPv4 的客户端。UDP、纯 IPv6 的客户端，容器看到的仍是网关。
- 绑客户端的端口失败时（这个 127.254 地址上不会有，宿主只是兜底）端口是宿主选的，与客户端的不同。
- 一个 127.254 地址只登记一个连接，连接结束就去掉；之后再连回这个地址的（容器主动连客户端）走宿主网络，不经过转发线程。
