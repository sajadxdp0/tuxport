# M9 之前：宿主 stdio 上的阻塞读只等宿主 fd（2026-10-27）

[锁和宿主 socket](53-locks-host-sockets.md)那一轮留下的推迟项：`tuxport-run` 交给 guest 的宿主 stdio（不带 `--pty`、stdin 不是终端时，`FileKind::Host`）上的阻塞读，用的是听所有通道、不限对象的等待，系统里每一次管道、PTY 的读写都会叫醒它。只影响 `tuxport-run`（开发、cargo test 和差分测试都用它），App 里没有这种文件。量下来（`target/herd/stdinidle.c`）：子进程阻塞在 `read(0)` 里，stdin 是没有数据的宿主管道；父进程自己写、读一个管道 2000 次，子进程被叫醒 137–451 次；与另一个进程来回 2000 次，被叫醒约 2600 次。

## 做法

- **只等宿主 fd**：等待时听文件类的通道，但不登记任何对象。对象上的修改不再叫醒它，请求所有通道的修改（比如 Machine 关闭）仍会叫醒它。宿主 fd 上的写不经过等待机制（放开 BKL 直接调用宿主的 write），不用改。

## 结果

上面两项都降到 0 次。标准基准都在噪声范围内。

## 测试

rootfs 测试新增一个用例：guest 里 dd 阻塞在读宿主 stdin 上，shell 用内建命令在一个 FIFO 上反复写读，dd 的自愿上下文切换次数不变，之后往 stdin 写一行照常读到。开始数之前先等 dd 停在读里（全量测试并行时它可能还在启动）。中途改过两次：

- 第一版用 busybox 的 `read` 内建命令读 stdin，改动前后都是 0 次：它先 poll，poll 的等待者登记的对象列表是空的，本来就不会被对象上的修改叫醒，所以改用直接调用 read 的 dd。
- 第二版的流量是 `echo x | cat`，全量 cargo test 时 Tier 0 下每次都有几次叫醒：musl 的 fork 在 clone 前后屏蔽所有信号，shell 起管道里的第二个进程时第一个正好退出，SIGCHLD 就被所有线程屏蔽，按规则叫醒所有等待者（见推迟项）。所以改成测量期间不起子进程的 FIFO 读写。

## 推迟项

- 发给进程的信号被所有线程屏蔽时仍叫醒所有等待者（[按对象唤醒](49-targeted-wakeups.md)起的推迟项），这一轮发现它比原来估计的常见：musl 的 fork 在 clone 前后屏蔽所有信号，进程 fork 的那一刻正好有子进程退出就会触发。shell 起管道、构建工具并行起进程时都可能遇到，每次都把系统里所有 poll、epoll、阻塞的读写、等锁的线程叫醒一遍。→ 已改：只叫醒 sigtimedwait、signalfd 的等待者（M9 之前：被屏蔽的信号只叫醒等它的线程），仍是全局的通道
