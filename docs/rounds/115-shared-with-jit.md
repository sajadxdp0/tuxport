# M9 之前：有 JIT 代码的进程也共用翻译（2026-10-30）

[同一个程序共用翻译](108-shared-translation.md)的推迟项：组里的成员一映射可写可执行的内存（JIT）就离开组，只剩它一个时组就关掉，所以几个 node 进程各翻译一份。

## 先量了一下

实验版引擎（`target/mem/splitinstr.py`，不提交）在翻译放回池里时按块的 pc 在不在可执行文件的映射里分类。node 要用 SIGKILL 结束才量得到：正常退出时 V8 先拆掉自己的代码区，那里的块就作废了。

| 负载 | 文件里的代码 | 别的（JIT 生成的） |
|---|---|---|
| `node -e 0` | 12.1 MB | 约 0 |
| node 的 JIT 热循环 | 22.3 MB | 0.1 MB |
| `npm --version` | 12.6 MB | 0 |
| Gemini CLI `--version`（两个 node 进程） | 40.2 MB、35.1 MB | 4.7 MB、2.7 MB |

V8 的解释器、内置函数和 ICU 都在 node 的程序文件里，所以 node 进程的翻译 89–99% 可以共用。MCP 服务器、Gemini 这类同时开好几个 node 进程的情形，每多一个进程就多 12–40 MB。

## 做法

见 §4.2 的"同一个程序共用翻译"。

- 组里的每个成员有一个标签（引擎按实例分配，1–65535）。登记过的可信文件映射里的块所有成员共用，翻译表里的键是 pc；别处的块（JIT 生成的、写过的代码）只对翻译它的成员有效，键是 pc | 标签 << 48。guest 的 pc 只有 48 位，查表时先排除更高的，所以两种键不会相同，guest 也伪造不出别的成员的键。
- 两种键都按 pc 散列，一次线性探测同时比两个键。先按 pc 找、没有再按带标签的键找的话，JIT 代码每次没命中跳转缓存都要多一次探测，第一个表项多半不在缓存里。
- 共用的块不链接到私有的块：共用块的链接桩在退出码里带一位标记（条件分支到桩的距离只用到 12 位，第 15 位空着），分发器据此不回填；建块时的链接也只找共用的块。作废的共用块的转发桩带同样的标记。私有的块可以链接到共用的和自己的块。
- 翻译模板分共用、私有两种：两种块的链接桩不同。
- 引擎有组里登记过的映射（排好、合并之后发布，不持锁读，换下来的等实例回到池里再释放），翻译时据此决定块是共用还是私有。登记的范围只增不减，读到旧的只会把块当成私有的，还是对的。
- 第二个成员加入时作废登记范围以外的块（上一个使用者留下的），私有的块留着。实例回到池里、保留翻译时去掉私有的块：只有同一个成员的私有块链接到它们，又没有线程挂着，不用转发桩；标签之后从头分配。
- 内核层：成员不可信的可执行映射记成它私有的范围（相接的合并）。私有的范围不能压着登记过的，登记的也不能压着别的成员私有的（`CodeGroup::admit`），不满足时离开组，和原来一样；别的成员的私有范围之间可以重叠，标签把它们分开。标签用完时组不再接受新成员，之后的进程另开一组。

## 结果

4 个 node 各跑一段会被 JIT 编译的代码再空闲（`target/mem/idle-node.sh`），用 `target/mem/memparts.sh` 量 tuxport-run 宿主进程：

| | 第 114 轮 | 之后 |
|---|---|---|
| 代码缓存 | 70.2 MB（5 个实例：20.0、16.6 × 3、0.5） | 20.7 MB（2 个：20.3、0.5） |
| App 的用量（RssAnon + RssShmem） | 190 MB | 119 MB |
| 峰值（VmHWM） | 312 MB | 190 MB |

0.5 MB 的那个是起 node 的 shell。第二到第四个 node 原来各多 16.6 MB 代码缓存，现在几乎不多：它们执行的大都是第一个翻译好的 node 程序文件里的代码。

计时（`target/mem/ab115.sh`，ab106.sh 加上 4 个 node 同时计算，与第 114 轮的二进制交替 3 轮）都在原来的范围里：

| 负载 | 之前 | 之后 |
|---|---|---|
| python / gcc / shell 起进程 / `git status` | 1.34–1.43 / 2.19–2.34 / 0.16–0.17 / 0.07–0.08 秒 | 1.35–1.37 / 2.18–2.23 / 0.16 / 0.07 秒 |
| `node -e 0` 之后 10 次 / 4 个 node 同时计算 | 0.41–0.44 / 0.45–0.48 秒 | 0.41–0.42 / 0.44–0.47 秒 |
| `java -version` / `go build` 冷编译 | 0.08–0.13 / 5.84–5.92 秒 | 0.08–0.09 / 5.75–5.84 秒 |
| Maven / Gradle 热构建 | 5.95–6.05 / 1.36–1.40 秒 | 5.88–6.02 / 1.35–1.42 秒 |

4 个 node 同时计算没有变快：后面几个进程原来也是拷贝翻译模板，不用重新翻译。这一轮省的是内存。单独一个 JIT 进程（Maven、Gradle、node）现在也在组里、JIT 代码带着标签，没有变慢：查表例程每探测一个表项多比一个键，共用块不链接到私有块的情形很少。

## 测试

- 引擎的单元测试 `members_share_file_code_and_keep_jit_code_apart`：两个成员共用文件里的块、各自执行自己的 JIT 代码，伪造别的成员的键是取指错误。内核层的 `code_groups_keep_private_code_apart_from_registered_files`：私有范围和登记的映射哪些可以重叠、哪些不接受。
- 差分测试 `shared-code` 的 `jit` 情形（父子进程在同一个地址各写各的代码）现在两个进程都留在组里，结果与原生相同。

## 推迟项

- 共用的块经由直接跳转进入私有的块时不回填链接，每次都退出到分发器。文件里的代码一般经由间接跳转进入 JIT 代码，没有量到这种情形。
- 每个成员都占一个标签，没有 JIT 代码的也是：不这样的话，它在登记范围以外翻译的块（比如映射刚改、还没核对的那一刻）就成了共用的。一个组接纳 65535 个成员之后另开一组。
- 成员跳到只有别的成员映射过、自己没有映射的地址时，执行的是那里的翻译（[同一个程序共用翻译](108-shared-translation.md)的推迟项，没变）。
- 几个 java 进程同时运行（Gradle 的 worker、Maven fork 出来的 JVM）现在也共用翻译，没有量。
