# M9 之前：拆 BKL（2026-10-26）

上一轮的结论是剩下的差距主要在 BKL。这一轮分几步把常用的路径从 BKL 下拿出来，每一步单独提交。

## 时间花在哪里

先给工作区加上按 syscall 统计持锁、等锁时间的临时插桩（`target/mem/bklinstr.py`），在各类并行负载上各跑一次（`target/mem/bklsurvey.sh`）：

| 负载 | 持锁或等锁最多的 |
|---|---|
| `go build` 冷编译 | clock_gettime 218 万次：持锁 0.41 秒、**等锁 2.5 秒**；nanosleep 2.5 万次，等锁 0.47 秒；futex 等锁 0.14 秒 |
| Maven 热构建 | mmap 2 万次，持锁 0.2 秒（每次平均 10 微秒）；clock_gettime 76 万次，持锁 0.14 秒、等锁 0.21 秒；futex 8.5 万次，持锁 0.08 秒 |
| `xargs -P4` 编译 Lua | mmap 17 万次、munmap 16 万次（cc1 的内存分配），合计持锁 0.51 秒、等锁 0.32 秒 |
| 并行 lstat 的 `git status` | 没能不持锁的 newfstatat 6646 次，等锁 0.31 秒 |
| 4 个同时 exec、4 个同时跑管道 | clone、execve、exit_group（上一轮） |

等锁的时间是各线程等锁的 CPU 时间之和，大多在空转的后台线程上（Go 的 sysmon、空闲的 P 不停地读时钟），不全在关键路径上。并行编译的伸缩已经接近原生：`xargs -P4` 编译 Lua 的 33 个文件，原生 P1 4.8 秒、P4 1.7 秒（2.8 倍），tuxport 16.8 秒、6.45 秒（2.6 倍），BKL 争抢在这里只占约 7%。

## 试过没有采用：被打断的线程不进内核

Maven 一次构建有 3.6 万次打断（munmap、mprotect 之后的 TLB shootdown 打断正在执行 guest 代码的线程），每次被打断的线程都要取 BKL（只为看看有没有信号），等锁一共 0.24 秒。试过让只为 shootdown 的打断不进内核：打断信号、fork 的快照这些要它停住的时候置一个标志，没有这个标志的打断回到运行循环开头、重新读代数就接着执行。

- 解除映射的一方原来等被打断的线程"不在执行 guest 代码"，现在它马上又回去了，可能一直看不到：guest-posix 测试里一个线程忙等 CPU 时钟定时器，另一个线程 munmap，解除映射的一方持着 BKL 等了下去（活锁）。改成等它"不在执行，或者打断之后离开过一次"（每个线程记着因为打断离开的次数）就好了。
- 但有更大的问题：被打断的线程不再睡下等 BKL，CPU 一直被占着。几个线程在 guest 代码里空转、主线程反复 mmap/munmap（`target/mem/unmapbench.c`，虚拟机 4 个核）：空转的不超过 3 个时两者都是每一对 3–4.6 微秒，没有收益；6 个时从 32–161 微秒变成 3.1–4.1 毫秒。线程数超过核数时，解除映射的一方要等宿主把没在运行的那个线程调度上来（一个时间片）；原来被打断的线程都睡下等锁，空出了核。手机上线程比核多是常态，Maven 也没有量出收益，撤回了。（最初量这组数时，一个卡住的实验进程在后台占着两个核，3 个空转线程就已经出现回退；后来在空闲的宿主上重新量过。）

留下了两样：guest 测试 `threads.c` 新增"一个线程一直在执行 guest 代码时另一个线程反复 munmap"；差分测试 `c-programs` 里 stat 那组的检查线程在主线程开始改目录之前先做一次检查，原来主线程不等它，负载重时原生一侧也会报"1 bad"。

## 做法

### 读时钟不取 BKL

vDSO 的时间函数只是 svc 存根（§7.2），Go 的 nanotime、JVM 的 `System.nanoTime` 每次都进内核。`clock_gettime`、`gettimeofday`、`clock_getres` 读宿主的时钟和线程自己的 CPU 时钟（`CLOCK_THREAD_CPUTIME_ID`，或者 `pthread_getcpuclockid` 编码出来的自己的 tid）时，在不持 BKL 的路径（`syscall::fast`，§6）里做完；进程的、别的线程的 CPU 时钟要用内核里的状态，照常取 BKL。在跟踪系统调用（`TUXPORT_STRACE`）时都走持锁的路径，好打印出来。

### futex 和睡眠不取 BKL

读时钟之后，`go build` 里等锁最多的是 nanosleep（等锁 0.44 秒）和 futex（0.23 秒），Maven 里 futex 持锁 0.1 秒、等锁 0.13 秒。

- **futex 的等待队列有自己的锁**（`Shared::futexes`），从 `Kernel` 里移出来：持有 BKL 时也可以再取它，反过来不行。检查 futex 的值和登记成为等待者在同一次持锁里做，唤醒也取它，持锁的和不持锁的路径之间不会漏掉唤醒。持锁路径的 FUTEX_WAIT、futex_waitv、FUTEX_CMP_REQUEUE 和线程退出时的 robust 链表、`clear_child_tid` 也都改成在这把锁里检查值。
- **不持 BKL 的 FUTEX_WAIT/WAKE（含 `_BITSET`）**：键就是宿主地址时才做，即这一页在线程的页表里可写（借来的写时复制的页要先换成自己的，只读的映射很少见，都交给持锁的路径），而且不在可以写的共享文件映射里（那里以文件和偏移为键）。第一版按整个地址空间记"有没有过可以写的共享文件映射"，`go build` 里的 futex 仍有六成走持锁的路径：Go 的每个工具链进程（go、compile、asm、link）都可写地共享映射一个 16 KB 的遥测计数文件。现在地址空间按范围记这种映射，新建、搬动（mremap）时重新统计，fork 时复制；拆掉的不必马上去掉，只是那里的 futex 走持锁的路径。只读打开的文件的共享映射以后也不能变成可写，不算在内。
- **不持 BKL 的 nanosleep、clock_nanosleep**（实时、单调、启动以来的时钟）。
- 等待的线程睡在自己的事件上，与持锁的等待一样被 futex 唤醒、信号和结束线程组叫醒。睡着时不标记在执行 guest 代码，解除映射的线程不必等它；`/proc` 里显示为睡眠（`Task::sleeping` 改成原子变量，内存上限的检查、给进程挑接收信号的线程也看得到）。不是被 futex 唤醒、也没到期就醒了（多半是来了信号）时，从队列里退出、交给持锁的路径重新做，由它处理信号和重新开始；nanosleep 交过去时带着原来的到期时刻（`TaskState::fast_sleep`），被信号打断时剩下的时间不从头算。

## 结果

### 读时钟不取 BKL

| 负载（交替运行） | HEAD | 之后 |
|---|---|---|
| `clock_gettime(CLOCK_MONOTONIC)`，单个进程（每次） | 127 纳秒 | 89 纳秒 |
| 同上，4 个进程同时 | 790–813 纳秒 | 87–89 纳秒 |
| `go build` 冷编译 | 6.33–6.42 秒 | 6.25–6.34 秒 |
| Maven 热构建、node | | 不变 |

（这一节最初记的 `go build` 对比用的基线二进制是更早的 883ea95，混进了上一轮翻译池的变化；上表是按提交前后重新编的基线、与下一步一起交替量的。）

### futex 和睡眠不取 BKL

`go build` 里 futex 取 BKL 的次数（持锁路径的等待每次被叫醒都要重新取一次）从 8868 降到 1843（剩下的多是被叫醒之后交回去的），nanosleep 从 2.3 万降到几百。

| 负载（交替运行） | 读时钟之前（ee55a06） | 读时钟之后（a9d0cd3） | 之后 |
|---|---|---|---|
| `go build` 冷编译 | 6.33–6.42 秒 | 6.25–6.34 秒 | 6.19–6.31 秒 |
| Maven 热构建 | 6.23–6.36 秒 | 6.23–6.29 秒 | 6.21–6.29 秒 |
| 4 对线程（4 个进程）同时 futex 乒乓，每个来回的中位数 | | 10.8 微秒 | 4.9 微秒 |
| 一对线程 futex 乒乓 | | 25.5–27.6 微秒 | 25.1–30.6 微秒（不变） |

一对线程时 BKL 本来就没有争抢，来回的时间是宿主线程睡下、被叫醒的延迟。`go build`、Maven 的关键路径上等锁不多，变化不大。

## 测试

- guest 测试程序 `posix.c` 新增时钟一项：单调时钟、`gettimeofday` 和 `CLOCK_REALTIME`、出错的参数，自己的 CPU 时钟的两种写法，以及在新线程里看另一个空转的线程的时钟。
- guest 测试程序 `threads.c` 新增 futex 和 nanosleep 一项：被信号打断、超时、值不对、被另一个线程唤醒，nanosleep 被打断时剩下的时间。差分测试 `c-programs` 新增共享文件映射里跨进程的 futex（父子进程各自映射同一个 memfd，宿主地址不同）。

## 推迟项

- mmap、munmap 仍持 BKL：`xargs -P4` 编译 Lua 时两者合计持锁 0.51 秒、等锁 0.32 秒，Maven 的 mmap 每次平均持锁 10 微秒。R1 的退路是地址空间的操作改用每个 mm 自己的锁（§16）。→ 私有匿名的宿主内存改为复用，mmap 每次持锁 2.5 → 1.3 µs，`xargs -P4` 里两者的等锁 0.28 → 0.17 秒（M9 之前：起进程和 mmap 的持锁时间）；仍持 BKL，8 核上量过 `-P8` 编译只差约 5%，不拆（M9 之前：8 核上的扩展性和 BKL 的交接）
- clone、execve、exit_group 仍持 BKL，几个进程同时起进程、跑管道时在这里排队（M9 之前：多进程并行）。→ 线程开始时不再持锁读宿主的 `/proc`、挂上翻译挪到锁外，4 个同时 exec 每次 414–474 → 376–402 µs（M9 之前：起进程和 mmap 的持锁时间）；等锁时最多让 4 个线程自旋，8 核上 8 个同时 exec 快 7%、跑管道快 13%（M9 之前：8 核上的扩展性和 BKL 的交接）；仍持 BKL
- 并行 lstat 的 `git status` 里仍有 6646 次 newfstatat 交回持锁的路径（等锁 0.31 秒）。
- futex 的键不是宿主地址时（可以写的共享文件映射、借来的写时复制页、只读的映射），以及读进程的、别的线程的 CPU 时钟，仍走持锁的路径。
- TLB shootdown 打断的线程仍要取 BKL 看有没有信号（Maven 一次构建 3.6 万次，等锁 0.24 秒）；让它不进内核在线程比核多时更慢，撤回了（见上）。
