# M9 之前：代码缓存只算一次（2026-10-30）

审完推迟项之后定下的方向：先做内存，再拆 BKL。[第二轮普查](70-survey-suites.md)的问题 5（每个进程各一份翻译，多进程负载的内存是原生的几倍）和 [AI 编程 CLI](103-ai-cli-survey.md) 的界面多占 1.5 到 5 倍，在手机上决定的是程序能不能跑完：App 的匿名内存到了上限，OOM killer 就要结束进程；系统内存吃紧时，LMK 按 App 的 RSS 挑要结束的 App。

这一轮先把多出来的内存拆开量，修掉其中一项白算的。

## 多出来的内存

- **怎么量**：`target/mem/memparts.py` 按宿主的 smaps 给 tuxport-run 的映射分类：128 MB 的共享映射是 Tier 1 的代码缓存，权限是 `rw-s` 的是写入用的视图，`r-xs` 的是执行用的视图（§4.2 的 W^X）；其余按匿名、文件、堆分。负载是 20 个空闲的 python3（`python3 -c 'import time; time.sleep(600)'`），原生对照在同一份仓库导出的容器里。
- **20 个空闲的 python3**：App 的用量（RssAnon + RssShmem，OOM killer 量的就是它）321 MB，原生 20 个进程的匿名内存合计 59 MB（每个 3 MB）。每多一个 python3，tuxport 多 15.4 MB：
  - 约 5.1 MB 是翻译出来的代码；
  - 约 5.1 MB 是同一份代码又算了一次：RssShmem 206 MB，正好是执行视图的 100.5 MB 加上写入视图的 100.5 MB。宿主的 RSS 按映射数页，代码缓存的一页经由写入视图写过、又经由执行视图执行过，就算两次。第 36 轮记内存时就看到过（"同一页算两次，实际约 42 MB"），当时没有处理；
  - 剩下约 5.1 MB 是匿名内存，比原生多约 2 MB，是翻译表、块的记录、跳转缓存和内核层的页表等。

## 试过没有采用：按写入量拆

第一版在引擎里每攒够 256 KB 写过的页就拆一次，放回池里时再全拆，不需要定时器线程。20 个 python3 的效果相同，但 Maven 热构建慢了 3%（交替 3 轮，6.20–6.33 → 6.37–6.48 秒），Gradle 慢 2%。宿主的缺页多了 36 万次（`jvm-warm.sh` 一共 125 万 → 160 万次），每次约 0.5–1 微秒。门槛放大到 1 MB、4 MB、16 MB，缺页也只少一点（155 万、152 万、144 万次）。改从执行视图读本身不多缺页：完全不拆时是 124 万次，与 HEAD 相同。

把 JVM 负载每一次写代码缓存的页和时刻记下来（423 万次，`target/mem/wtrace-jvm.txt`）离线模拟（`target/mem/wsim.py`），问题在 JIT 负载自己：一个 JVM 实例每秒写约 8 万次，几乎都是单字的回填链接和作废，分布在 4500 到 6000 个不同的页上，代码缓存用到 96 MB。按量拆的话这些页一拆就要重新缺页；"连续两个周期没写才拆"也省不了多少，写的页之间没有局部性。按时间拆的代价是每秒最多每页缺一次：

| 策略（模拟） | 比不拆多的缺页 | 平均多算的内存 |
|---|---|---|
| 每攒 64 页（256 KB）拆一次 | 43 万次 | 1.7 MB |
| 每攒 1024 页拆一次 | 34 万次 | 9.4 MB |
| 每 0.5 秒拆一次 | 18 万次 | 9.9 MB |
| 每 1 秒拆一次 | 16 万次 | 17.8 MB |
| 每 2 秒拆一次 | 13 万次 | 34.4 MB |
| 每 1 秒，连续两个周期没写才拆 | 11 万次 | 45.1 MB |
| 不拆 | 0 | 183 MB |

取每秒一次。OOM killer 量的用量反正扣掉了还没拆的页，间隔只影响 LMK 看到的数和多出的缺页。实测 `jvm-warm.sh` 的缺页 133 万次，比 HEAD 多 9.5 万次。

## 做法

- **定期拆掉写入视图里写过的页**（`dbt.c` 的 `struct written`，`tuxport_dbt_unmap_written`）：
  - 引擎在每次同步代码之后（`sync_range`、`sync_all`、`publish_link`，以及作废、恢复停放块时直接同步的几处）记下写入视图里写过的宿主页（每个实例一张 4 KB 的位图，原子操作，不持锁回填链接的线程也记）。
  - 内核层的定时器线程有 guest 线程在运行时每秒拆一次所有实例记下的页（`oom::unmap_code_views`）：在共享内存上 `MADV_DONTNEED` 只拆掉页表项，内容还在，之后再写只是重新缺一次页。所有线程都进入等待之后再拆一次，然后和 OOM 检查、平均负载的取样一样停下，下一个要执行 guest 代码的线程叫醒它。
  - 清空的实例（放回池里时不保留翻译的）在 `MADV_REMOVE` 之后顺手清掉记录。
  - 宿主不允许双映射、退回 RWX 时没有写入视图，什么也不做。
- **OOM killer 和 cgroup 量的用量扣掉还没拆的页**（`oom::app_memory`）：两次拆之间新写的页在 RssShmem 里仍算两次，引擎知道是哪些页（`tuxport_dbt_written_bytes`），量的时候扣掉。内存上限的检查、`memory.current`、`memory.peak`、`memory.stat` 的 shmem 都用它。hal 的 `memory_footprint` 去掉了，免得有人直接用宿主的数。启动 20 个 python3 时，guest 看到的 `memory.peak` 也不再多算了（313 → 213 MiB）。LMK 看的宿主 RSS 只能等拆掉之后才变，见推迟项。
- **改写条件分支和回填链接之前从执行视图读原来的指令**（`relink_word`，不持锁回填时的 `again`）：原来从写入视图读。在共享映射上读缺页时，宿主会顺带映射附近的十几页（fault-around），这些页没有被记下来，要等下一次拆到它们所在的范围才拆掉。改之前 20 个 python3 空闲时，写入视图还剩约 10 MB，改之后不到 0.5 MB。
- **16K 页的宿主上清空实例时交还代码缓存**：清空的实例 `MADV_REMOVE` 的起点按 guest 的 4 KB 页（`TUXPORT_PAGE_SIZE`）对齐，在 16K 页的宿主上起点可能不对齐，madvise 返回 EINVAL，代码缓存就一直占着（[多进程并行](36-parallel-processes.md)那一轮起）。改为按宿主的页大小对齐。

### 剩下的内存在哪里

- **20 个空闲的 python3**：每个进程的翻译约 5 MB，20 个各一份（问题 5 本身），加上每个进程约 2 MB 的表和内核层的开销。同一个程序的进程之间共用翻译能省掉大部分：tuxport 没有 ASLR，同一个程序的各个进程地址相同，"同一版本的程序文件里的块不再核对"（§4.2 的翻译保留）也已经有了。难在作废：一个进程改了自己的映射，不能影响别人。
- **Codex 的界面**：只有两个大进程，node 写的启动脚本（guest 里的 RSS 56 MB）和 Rust 的 codex（167 MB），却有 20 个代码缓存的实例。最大的两个是 codex 本身的翻译 43.9 MB、node 的 21.9 MB，6.3 MB 的一个，其余 17 个都不到 2 MB（池里保留的 sh、tmux、ps 等）。这里共用翻译帮不上忙，多占的是一个大程序翻译出来的代码：翻译后的代码是 guest 代码的 6 倍多（M7 量过），每条访存有内联的 TLB 检查、回填桩和退出桩。要省就要提高翻译代码的密度（M7 起推迟的"退出桩压缩"）。
- 池里保留的翻译最多 64 MB 代码（连同表等约 85 MB），界面离开 1 分钟或者内存紧张时释放（[onTrimMemory](37-trim-memory.md)）。

## 推迟项

- LMK 看的宿主 RSS 在两次拆之间（最多 1 秒）仍把这段时间里写过的页算两次，宿主的 VmHWM 也是（20 个 python3 同时启动时 VmHWM 仍是 330 MB）。OOM killer 和 cgroup 的用量扣掉了这一部分。
- Tier 0 的原生指令桩（`native.c`，所有线程共用一块 2 MB 的缓存）也是双映射，写过的页仍算两次；通常只用到几十 KB。
- 写过、还没执行过的页拆掉之后哪个视图也不算（RssShmem 少算），只是零星几页。
- JIT 负载每秒多几千次缺页（`jvm-warm.sh` 比 HEAD 多 9.5 万次），Maven、Gradle 的计时在波动范围内。
- Claude Code 的界面这一次在 tmux 里没有起来（没带第 103 轮模拟服务的环境变量），没量。
- 每个进程各一份翻译（问题 5）、翻译代码的密度，见上面的「剩下的内存在哪里」。→ 密度：桩里的 guest pc 改放数据字，每条 guest 指令翻译成的宿主字数 7.5–8.3 → 约 6，20 个 python3 的代码 100 → 78 MB（M9 之前：翻译代码的密度）；每个进程各一份翻译已改为同一个程序共用（M9 之前：同一个程序共用翻译）
