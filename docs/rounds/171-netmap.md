# M9 之前：经由虚拟网卡的连接：socket 层的地址映射（2026-11-01）

[容器网络的普查](169-container-network-survey.md)定下的方案 1 的第二步。[上一轮](170-netdev.md)之后 docker、podman 的 bridge 网络建得起来、容器起得来，但数据包不经过虚拟网卡：容器之间、外层到容器都是 "Network unreachable"，docker 的 `-p` 容器起不来，podman 自定义网络的 aardvark-dns 绑不上网关地址。这一轮在 socket 层把虚拟设备上的地址换成宿主上的回环地址，连接、数据报都经由宿主的回环接口，与[网络命名空间](122-net-namespaces.md)换 lo 的地址是同一个办法。

## 做法

- **宿主上的地址**（`core/kernel/src/netns.rs`）：
  - 新的网络命名空间原来就有一段宿主上的回环地址 127.a.b.0/24（127.0.0.x 是 127.a.b.x）。它的虚拟设备上的地址（容器的 eth0）都对应 127.a.b.1：与通配地址绑的是同一个，所以监听 0.0.0.0、`::` 的服务从 eth0 的地址也连得到。绑在 eth0 的地址上时宿主上同样是 127.a.b.1，socket 记下虚拟地址，getsockname 报告它。
  - 开机时的命名空间里的虚拟地址（docker0 的 172.18.0.1、podman 各个网络的网关）每个各分一个 127.255.x.y（用到时分配；新命名空间的段不再取 127.255）：aardvark-dns 在每个网关的 53 端口上各绑一个，不能共用。宿主上监听通配地址的服务本来就收得到这些地址。
- **目的地址**（connect、sendto）：先看是不是哪个命名空间的虚拟地址，要有经由虚拟设备的路由（没有是 ENETUNREACH）：
  - 别的新命名空间的 → 它的 127.c.d.1；开机时的命名空间的 → 它的 127.255.x.y；自己的 → 自己的 127.a.b.1。
  - 不是谁的虚拟地址：经由网关的路由（容器的默认路由）到得了的交给宿主网络，地址不换，socket 也不先绑回环地址（绑了就出不去）；在直连网段里却没有这个地址的马上是 EHOSTUNREACH（Linux 要等 ARP 超时）。
  - 开机时的命名空间里只看经由虚拟设备的路由：宿主的网段照旧归宿主。
  - 低端口映射（[第 156 轮](156-low-ports.md)）按目的地所在的命名空间的登记表换（容器里监听 80 的 nginx 从别的容器、外层都连得到），收到的数据报按来源所在的命名空间换回。
- **源地址**：还没绑定的 socket 在 connect、sendto 之前先绑：
  - 新的命名空间里绑它的 127.a.b.1（原来就这样），所以对方看到的来源换得回这个容器的地址；连自己 eth0 的地址时绑 127.a.b.254，两边都换回 eth0 的地址。
  - 开机时的命名空间里连容器时绑网关地址在宿主上的那个 127.255.x.y：容器里看到的对端是 172.18.0.1，与原生一样（docker-proxy 连容器也是这样）。getsockname 在连接之前仍报告通配地址。
- **反过来**（getsockname、getpeername、accept、recvfrom、`/proc/net`）：宿主地址按"谁在看"换回：别的命名空间的 127.c.d.1 换成那个命名空间面向自己的地址（在自己有直连路由的网段里的那个）；127.255.x.y 换回网关地址；经由宿主网络出去的连接，本端的宿主地址换成这个命名空间发往对端时的源地址（路由的首选源地址，没有时取出口接口的地址，`inet_select_addr`）。connect 给的对端原样记下，getpeername 报告它。
- **绑通配地址的数据报 socket**：busybox 的 ping 没有 `CAP_NET_RAW`（podman 的容器默认没有）时退回 ping socket，先 `bind(0.0.0.0:0)`；Java 的 DatagramSocket 也这样。在宿主上绑 127.a.b.1 的话发不到外面（EINVAL），所以新命名空间里的数据报 socket 显式绑通配地址、端口为 0 时，宿主上也绑通配地址（只是临时端口，不会把容器的服务暴露出去），第一次发往外面时由宿主自动绑定的也算。这种 socket 发往映射的目的地时用 `IP_PKTINFO`（IPv6 socket 用 `IPV6_PKTINFO`）把源地址指定成 127.a.b.1，对方看到的来源和回去的数据报才对。它 connect 到映射的目的地（busybox 的 nslookup 先绑再连）时宿主 socket 不连接——连了本端就定成宿主选的 127.0.0.1，回来的数据报对不上——由内核层记下对端：不带地址的发送发往它，收到的不是来自它的丢掉，与 Linux 已连接的 UDP 一样。
- **`SO_ATTACH_FILTER`**、`SO_ATTACH_REUSEPORT_CBPF`：`struct sock_fprog` 里指向指令的指针换成宿主上的（原来原样交给宿主，EFAULT）。dockerd 在 `-p` 的监听 socket 上先装一个丢包的过滤器，起 docker-proxy 之后去掉；原来这里失败，`-p` 的容器起不来。

## 测试

- 新的差分测试组 `netmap`（原生一侧是特权容器，数据包真的经过 bridge）：开机时的命名空间里一个 bridge，两个新的网络命名空间 A、B 像容器一样挂在上面，测 TCP、UDP、低端口、ping 在容器、外层、网关之间连不连得上和两边看到的地址，各种到不了、绑不了的情形。两个执行层下都与原生逐字相同。原生上 bridge 不指定 MAC 时，删掉一个端口 MAC 就可能变，ARP 缓存对不上、连网关要超时，所以像 docker 一样指定 MAC；A 没了之后 B 连 A 的地址原生要等 ARP 超时（tuxport 马上 EHOSTUNREACH），这一项不比。单元测试 `netns` 测各个方向的地址换算。
- 普查（与原生对照）：
  - docker（`"iptables": false`）：容器之间、外层到容器、`-p 8080:80` 都与原生一致，不同的只剩容器里 ping 外层的网关通了（见推迟项）和自定义网络按名字解析（第 3 步）。 → 按名字解析通了（M9 之前：nftables 的子集和 socket 层的 DNAT）
  - podman（`firewall_driver = "none"`）：容器之间、外层到容器、按名字解析都与原生一致，不同的是 ping 外层的网关和 `-p` 时占着端口的监听（第 4 步），nftables 驱动仍是第 3 步。 → nftables 驱动能用了，`-p` 经由 127.0.0.1 和外层地址也通了（M9 之前：nftables 的子集和 socket 层的 DNAT）

## 推迟项

- 新的命名空间里所有虚拟地址都是同一个宿主地址：同一个端口不能一个绑 127.0.0.1、一个绑 eth0 的地址（EADDRINUSE，Linux 可以）；绑 127.0.0.1 的服务从别的容器也连得到（Linux 连不到）；有几个虚拟地址的容器，别人看到的是面向自己的那个。 → TCP 的监听按绑的地址判断，只绑 127.0.0.1 的从别处连不到了（M9 之前：各个网络命名空间的端口互不相干）；同一个端口绑两个地址仍不行
- （审推迟项时发现，写这一篇时没有发现）外层命名空间监听 0.0.0.0:P 时，新命名空间里绑同一个端口是 EADDRINUSE：podman、docker 内外同端口的 `-p` 容器起不来。 → 新命名空间的端口在宿主上另选，修了（同上）
- 容器经由默认路由出去的直接走宿主的网络，相当于总有 NAT：防火墙关着时也通（原生 docker 的 `"iptables": false`、podman 的 `firewall_driver = "none"` 时不通）。经由宿主网络出去的连接的本端是宿主选的地址，对方看到的是手机的地址。
- 宿主上绑通配地址的数据报 socket（上面那种）在宿主的所有接口上收得到发给那个临时端口的数据报；它 connect 到映射的目的地之后，ICMP 错误（对方没有监听时的 ECONNREFUSED）收不到。
- IPv6 的虚拟地址（`fd00::` 这种）没有映射：连、绑都不行；只有经由虚拟设备的 IPv6 路由出去的交给宿主网络。
- 直连网段里没有的地址马上是 EHOSTUNREACH，不等 ARP 超时；没有 ARP、邻居表。
- 新命名空间里发给自己的虚拟地址的 UDP 收不到回答（客户端绑在 127.a.b.254，回答发往 127.a.b.1；写这一篇时没有发现）。 → 修了（M9 之前：nftables 的子集和 socket 层的 DNAT）
- 组播、广播不经过 bridge。
- raw ICMP 的错误匹配（汇集点里）只换自己的回环段：别的容器的地址引起的 ICMP 错误可能对不上连接。
