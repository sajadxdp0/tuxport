# M9 之前：别的负载和文件操作（2026-10-26）

前几轮盯着编译、python 循环和起进程。这一轮先把各类负载各跑一次（`target/mem/survey.sh`，原生一侧在同一台虚拟机的 Alpine 容器里跑同一组命令；仓库在本地卷上），看哪里离原生还远：

| 负载 | 倍数 | 负载 | 倍数 |
|---|---|---|---|
| `find`、`du` | 约 1 | `awk` 循环 | 2.8 |
| `tar` 只读 | 1.4 | lua 循环 | 2.0 |
| `cp -r` 再 `rm -rf` | 2.4 | python 启动 / 循环 | 3.2 / 4.7 |
| `grep -r` | 3.0 | node 启动 / 计算 | 3.1 / 2.6 |
| `gzip` | 2.0 | java 启动 / 计算 | 4.0 / 2.8 |
| sqlite 内存库 / 文件库 | 3.8 / 2.7 | gcc 编译 hello | 2.9 |

## 做法

### java 启动（§4.2）

`java -version` 连跑 3 次的剖析里，分发器自己占了 31%，几乎都在同步指令缓存的 `dsb ish; isb` 上：3 次一共装进 12 万个块、链接退出 16.5 万次，每次链接都完整同步一次，要等作废广播完成。

- **链接点不等同步完成**：单独改写的链接点只做 `dc cvau`、`ic ivau`，不等它完成，也不做 `isb`。改写的线程接着直接进入目标块，用不着新指令；别的线程在看到新指令之前执行的是旧指令，退出到分发器照样找到目标块。一个线程退出时发现链接点已经改好了（它还执行了旧指令），才完整同步一次。新块本来就要同步时，链接点随它一起。
- **Tier 0 认不认识一条指令按指令字缓存**：翻译时问 Tier 0 要把这条指令执行一遍，占了 java 启动的 2%；回答只取决于指令字，每个线程缓存 4096 项。
- node 启动没有改：`node -e 0` 5 次有 6.6 万次单条交给 Tier 0、2.7 万个块因为 V8 改写代码而作废，记为推迟项。

### 文件操作（§8.1）

`cp -r` 一份 python 标准库再 `rm -rf` 的剖析里，SQLite 占 35%（新建 14%、删除 9%、stat 8%）。为此写了微基准 `target/mem/fsbench.c`：在一个目录里逐个新建、stat、改名、删除 2000 个文件，以及新建并写 4 KB、mkdir、rmdir。每个元数据操作是一个事务，用 Rust 直接量 SQLite（同样的表、同样的语句）：

| 每个操作 | 微秒 |
|---|---|
| 每个操作单独提交（现在的做法） | 15.8 |
| BEGIN、COMMIT 也预编译 | 14.8 |
| 独占锁模式（不加 fcntl 锁，只能一个进程用） | 13.0 |
| 多个操作一个事务，每个操作一个保存点 | 1.86 |
| 多个操作一个事务 | 1.16 |

贵的是提交本身：每次提交把改了的 4 个左右的页写进 WAL（每页两次 pwrite），再加 WAL 索引的 4 次 fcntl 加解锁。

- **推迟提交**：写事务打开之后最多推迟 5 毫秒提交，期间的每个操作是一个保存点，出错或者内核层 panic 时只回滚它自己（`Op` 守卫）。到点时由下一个操作或者定时器线程提交；guest 的 `fsync`、`fdatasync`、`sync`、`syncfs`，`Machine::sync`、`trim_memory`（还没接到 Android 的 `onTrimMemory`；→ 已接上，M9 之前：onTrimMemory）和关闭时立即提交。App 被杀掉时最多丢失最后几毫秒的元数据修改，仓库仍然是某次提交时的完整状态。
  - 删除最后一个链接时，object 等提交之后再删。
  - 提交之前被杀掉时，新建的 inode 随事务丢失，object 却留下了；编号以后再分配给目录时它就永远留下了。`lock` 文件里记着还没提交的写事务新分配的 inode 编号范围，开机时删掉其中没有 inode 行的 object；新建 object 时已经有同名的就清空接着用。
  - 别的 tuxport 进程也在用仓库时不推迟：`lock` 文件里记着使用者数，打开仓库时发现已经有别人，先等它提交推迟的写事务（空的 `BEGIN IMMEDIATE`），它看到计数之后也每个操作立即提交。
- **刚建好的文件不再截断**：`O_CREAT | O_TRUNC` 新建文件时，内核层对刚建好的空 object 又 ftruncate 了一次。ext4 把截断到 0 之后又写过的文件当成整个替换，关闭时立即开始回写：新建并写 4 KB 的文件比只新建慢 18 微秒，全花在 close 上。
- **开机清理已删除的 inode 合成一个事务**：原来每行单独提交两次，`rm -rf` 过几千个文件之后，下次启动要多花几十到几百毫秒。

## 结果

### java 启动

测量（`target/mem/startab.sh`，3 轮交替）：`java -version` 3 次 0.20 → 0.18 秒，`node -e 0` 3 次 0.213 → 0.207 秒，python 启动 5 次 0.63 → 0.623 秒，java 计算 1.357 → 1.327 秒；`ab.sh` 的几项没有变慢（`go build`、Maven 各快约 2%）。剩下的同步是新块装进表之前的那一次（多线程时必须在别的线程能跳过去之前完成，约 8%），以及等翻译锁的自旋（约 4%）。

### 文件操作

| 每个操作（微秒） | 原生 | HEAD | 之后 |
|---|---|---|---|
| 新建空文件 | 8 | 28.7 | 13.4 |
| 新建并写 4 KB | 7.5 | 43–51 | 17–19 |
| stat | 0.8 | 3.6 | 2.3 |
| 改名 | 9.5 | 21 | 6.0 |
| 删除 | 3.3 | 24 | 6–9 |
| mkdir / rmdir | 9.3 / 5 | 21 / 19.5 | 5–9 / 4.5 |

| 负载（`target/mem/fsab.sh`，3 轮交替） | 原生 | HEAD | 之后 |
|---|---|---|---|
| `cp -r` 再 `rm -rf`（python 标准库） | 0.045s | 0.12–0.13s | 0.07s |
| `tar x` 再 `rm -rf` | 0.05s | 0.15–0.16s | 0.09–0.10s |
| 新建 500 个空文件、`chmod`、删除 | 0.01s | 0.04–0.05s | 0.01–0.02s |
| `git init`、`add`、`commit` 一份 python 标准库 | — | 1.21–1.25s | 1.06–1.07s |

### 两项合在一起

两项合在一起再量一次（`startab.sh` 3 轮、`ab.sh` 2 轮交替）：`java -version` 3 次 0.20–0.21 → 0.17 秒，`node -e 0` 3 次 0.22–0.25 → 0.20–0.21 秒，`go build` 6.45 → 6.33 秒，python、gcc、shell、Maven 不变。

之后 `cp -r` 的剖析里提交只占 0.6%，剩下的主要是宿主上建、删 object（各约 13%）和复制数据（22%），原生也要做这些。

## 测试

- 被杀掉时的一致性：guest 里循环新建、改名、`rm -rf`，随机时刻 `kill -9` 掉 tuxport-run，再用 `target/mem/fsck.py` 检查仓库，都没有问题。第一版没有记新分配的编号范围时，多出来的 object 每次增加几个。
- 单元测试测推迟提交和提交之前被杀掉。第一版把"刚建好的文件不截断"写在了 `open_store` 里，经由 `/proc/self/fd` 重新打开 memfd 时也走那里，`O_TRUNC` 没有截断，差分测试的 compat 组发现了；改成只在 openat 新建文件的地方去掉 `O_TRUNC`。

## 推迟项

- node 启动：`node -e 0` 5 次有 6.6 万次单条交给 Tier 0、2.7 万个块因为 V8 改写代码而作废，还没查是哪些指令。→ 已查明并补上（M9 之前：node 启动）：交给 Tier 0 的多是 outline atomics 里的 STXR，作废的块多是核对时共享库还没映射，不是 V8 改写代码
- 文件操作剩下的差距在宿主上：object 都在一个目录里，新建、删除都要拿这个目录的锁；删除 object 也在持 BKL 的提交里做。→ 删除 object 已交给后台线程（M9 之前：文件操作的宿主开销）；object 仍都在一个目录里
