# M9 之前：多进程并行（2026-10-26）

单个进程起进程已经和原生差不多（spawnbench 的 exec 145 微秒，原生 145），几个同时起时差得多：4 个 spawnbench 同时 exec，每次 470–520 微秒（原生 158）；4 个同时跑 shell 管道，每次 2200–2300 微秒（原生 565）。`make -j`、`xargs -P` 这类负载就是这种情形。

## 时间花在哪里

- **BKL**：按 syscall 记下持锁时间，每起一个进程持锁约 80 微秒（execve 23、exit_group 22、clone 17），4 个同时跑时锁大半时间有人拿着。execve 和退出时取驻留内存的样（`ru_maxrss`）各要 4 次 mincore，持着 BKL 等宿主的 mmap_lock，而别的进程正在锁外 munmap（宿主剖析里 munmap 占 12.7%、mmap 9.5%，都在争同一把 mmap_lock）。
- **翻译池**：池里最多 6 个实例。4 个管道同时跑时，sh、cat、sort、grep、wc 同时各有好几个在跑，放回池里时互相挤掉，常常拿不到同键的实例：一次 pipe4 翻译了 22 万个块。

## 试过没有采用：池的上限连同翻译表一起算

池的上限连同翻译表、块的记录和指令字一起算（同样 64 MB）。`xargs -P4` 编译 Lua 慢了 4%：cc1 的实例连表有 30–50 MB，超过上限一半的只在不挤掉别人时保留，68 次里 21 次没能保留。仍只算代码，表等另外约多三分之一。

## 做法

- **翻译池放 16 个实例**（§4.2 的"翻译保留"）：pipe4 翻译的块 22 万 → 2.1 万。不保留的实例清空时，块的记录和指令字用过的页也交还宿主（原来只交还代码缓存），池里空着的实例不再占着上一个大程序留下的这些内存。
- **驻留内存峰值的取样**（§6）：要量的几段合计不超过 1 MB 时不量，按全部驻留算（最多多算 1 MB）；fork 出来、不到一个时钟滴答就 execve 的进程不量它自己的匿名内存，那里只有 fork 之后写过的几页。execve 的持锁时间 23 → 14 微秒，exit_group 22 → 10 微秒。第一版把 fork 的时刻记在 `Mm` 的新字段里，node 热启动慢了 3%，原因没有查清；改用线程组里已有的创建时刻和 execed 标志之后不再慢。

## 结果

| 负载（交替运行） | 原生 | HEAD | 之后 |
|---|---|---|---|
| 4 个同时 exec（spawnbench，每次） | 158µs | 466–523µs | 375–416µs |
| 4 个同时跑管道（每次） | 565µs | 2180–2307µs | 1627–1848µs |
| `xargs -P4` 编译 Lua 的 33 个文件 | | 6.23–6.27s | 6.27–6.30s |
| 单个 fork、exec、spawn、管道，shell 脚本，`xargs -P1` | | | 不变 |
| node 热启动 10 次、node 计算，gcc 编译 lvm.c，Maven | | | 不变 |

内存：跑一遍 node、python、java、gcc、sqlite、lua、git、perl 和几条管道之后，tuxport-run 的 VmRSS 109 → 203 MB，多出来的是池里多留下的翻译：RssShmem 4 → 84 MB（代码缓存双映射，同一页算两次，实际约 42 MB），RssAnon 43 → 57 MB（翻译表等）。峰值（VmHWM 205 MB，java 运行时）不变。

剩下的差距主要是 BKL 本身：现在每起一个进程持锁约 63 微秒（clone 17、execve 3 次合计 14、exit_group 3 次合计 10、缺页等 8），4 个同时跑时锁有六成时间有人拿着；clone 复制地址空间要几次宿主 mmap，同样要等 mmap_lock。再往下要拆 BKL（比如地址空间的操作改用每个 mm 自己的锁），不是小改动。

没有新增用例。

## 推迟项

- BKL 拆分：起进程、退出、缺页这些路径的持锁时间占了 4 路并发的大半。→ 先拆了读时钟、futex 和 nanosleep（M9 之前：拆 BKL）；起进程、退出、缺页、mmap/munmap 仍持 BKL
- 池里保留的翻译（代码最多 64 MB，连同表等约 85 MB）在 App 收到 `onTrimMemory` 时还不会清空。→ 已补上（M9 之前：onTrimMemory）
