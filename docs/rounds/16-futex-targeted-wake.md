# M9 之前：futex 定向唤醒（2026-10-25）

原来任何修改都会在释放 BKL 时叫醒所有正在等待的线程，futex 唤醒也一样。

## 做法

现在 futex 的等待项记下等待线程的事件，FUTEX_WAKE 只通知被唤醒的线程，futex 等待者也不再被别处的修改叫醒（§6）。其余的等待（管道、socket、epoll、wait4 等）仍是全部叫醒。→ 后来按文件、管道、子进程、线程结束分了通道（M9 之前：多线程共用翻译和定向唤醒、fork 写时复制）；poll、epoll 的等待者仍被所有文件类的修改叫醒（只等 `EPOLLEXCLUSIVE` 关注的 epoll_wait 除外，M9 之前：独占的唤醒）；后来 poll、epoll 和阻塞的读写都只被它们等的对象上的修改叫醒（M9 之前：按对象唤醒）

## 结果

- 两个线程用互斥锁和条件变量来回传递 10 万次：3.74 → 2.97 秒（原生 1.8–2.1 秒），20 万次等待里"全部叫醒"只剩 12 次。
- JVM 受益最大：Maven 热构建 17.5 → 15.7 秒，Gradle 热构建 6.1 → 4.8 秒；`go build` 冷编译 16.7 → 16.3 秒（M8 时是 19.2 秒）；`git status` 不变，它的线程争用在 BKL 本身。
- Gradle 那次运行里剩下的"全部叫醒"约 3.2 万次（等待 7.5 万次），每次白醒十几微秒，给每种对象建自己的等待队列的收益已经不大。拆分 BKL 仍放到发布之后（R1）。→ 后来提前拆了一部分（M9 之前：多线程共用翻译和定向唤醒、不持 BKL 的 stat、拆 BKL）
