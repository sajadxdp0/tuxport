# M9 之前：宿主内存的接缝（2026-10-30）

[访存检查和翻译表](23-tlb-checks.md)的推迟项：mremap 扩大映射时，新增的部分是另外申请的一段宿主内存，与原来的不连续。跨过这道接缝的访问交给 Tier 0；共用一次检查的访存组（§4.2）跨接缝失败两次，整个块就重新翻译、不再分组，以后处理什么数据都慢。这一轮先量它在真实负载里的影响，结论是不改：接缝很常见，但真实负载里最多损失 1.4%。

## 微基准

`target/mem/seam.c`：同一个循环遍历 8 MB 的结构体数组，每个元素在同一个基址上读三个字段（一条 `ldr` 加一条 `ldp`，Tier 1 编成一组）。数组分别是一次映射的、映射一半再 mremap 扩展的、realloc 从 256 KB 一步步翻倍长大的（musl 的大块走 mremap），最后再遍历一次一次映射的：

| 数组 | Tier 1 | 原生 |
|---|---|---|
| 一次映射 | 0.90–0.92 ns/元素 | 0.45 |
| mremap 扩展 | 1.26–1.28 | 0.46 |
| realloc 长大 | 1.27–1.33 | 0.45 |
| 一次映射（最后） | 1.27–1.37 | 0.46 |

循环跨过接缝失败两次之后被拆组，之后遍历连续的数组也慢了四成。python 的 list 不受影响：用 append 长大的 list（指针数组一步步 realloc）和一次分配的遍历都是 19–21 ns/元素，解释器每次只读一个指针，构不成组。

## 真实负载

实验版引擎（`target/mem/seaminstr.py`，不提交）在回填例程判断"两页宿主地址不连续"的地方单独计数；`SEAM_NOSTRIKE=1` 时这种失败只把这一条交给 Tier 0，不拆组，相当于没有接缝的惩罚。同一个二进制开、不开它交替各两轮（`target/mem/seamab.sh`）：

| 负载 | 拆组（不开 / 开） | 接缝失败（不开 / 开） | 耗时（不开 / 开） |
|---|---|---|---|
| python、gcc、json、sqlite、node 依次跑一遍 | 41 / 23–24 | 142 / 5104 | 没有可测的差别（node 0.56–0.57 / 0.59–0.62 秒） |
| Maven、Gradle 热构建 | 642–699 / 29–34 | 3.7 千 / 4.4–4.8 万 | Maven 5.93–5.95 / 5.85–5.86 秒，Gradle 不变 |
| `go build` | 78–131 / 6 | 520–866 / 1434–1957 | 5.90–5.95 / 5.92–5.98 秒 |

接缝比原来以为的多：JVM 和 Go 里九成以上的拆组都是它造成的，而它们几乎不调用 mremap（`go build` 一次也没有）。另一个来源多半是先保留一大段地址、再用 `mmap(MAP_FIXED)` 分块提交（HotSpot 的 `os::commit_memory`、Go 运行时的 `sysMap` 都这样做）：每一块在 tuxport 里都是一段新的宿主内存，相邻两块之间就是接缝。mremap 在 python（一次 json 的负载 60 次）、node（33 次）、gcc、sqlite 里有。

不拆组的时候也只有 Maven 快了 1.4%，别的都没变：被拆组的块多半不热。

## 能做但没做的

- 宿主内存保持连续：mremap 扩展时用宿主的 `mremap`（`MREMAP_DONTUNMAP`，不持锁读写的线程还拿着旧地址也不会出错；Android 12 之前的内核没有它，照旧另起一段）把整段搬到一段更大的新内存里；`MAP_FIXED` 覆盖私有匿名映射的一部分时清零原来的宿主页接着用，不另起一段。写时复制借出、借来的页（它们按宿主地址登记）、拆开的 VMA 都要处理，是内存管理里最复杂的那部分，收益只有上面的 1.4%。
- Tier 1 遇到接缝不拆组（实验里的做法）：每次接缝失败都交给 Tier 0 执行一条，node 反而略慢；一个压在接缝上、被反复访问的结构体每次都要退出，比拆组更糟。

## 推迟项

- 「能做但没做的」里的两种做法。JIT 负载的拆组主要来自分块提交，要改的话先做 `MAP_FIXED` 覆盖时复用宿主页。
