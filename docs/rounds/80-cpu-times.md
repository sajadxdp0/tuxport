# M9 之前：CPU 时间不倒退（2026-10-28）

[翻译后代码里的访存](30-translated-access.md)那一轮记下的待查项：LTP 的 times03 偶尔看到进程的用户态 CPU 时间倒退一个滴答（111 → 110）。它从[剩下的小缺口](18-small-gaps.md)那一轮起才通过，之后保存下来的全量结果里 33 次失败了 2 次（第 30、44 轮），记在[已知的偶发失败](../milestones.md#known-flaky-tests)里。

## 原因

线程的 CPU 时间分两处取。总数是宿主线程的 CPU 时钟，精确到纳秒；内核态的部分是宿主记的内核态时间，线程自己读用 getrusage，读别的线程（times、`RUSAGE_SELF` 汇总所有线程时，自己也算在里面）只能读 `/proc/self/task/<tid>/stat`，按时钟滴答（10 毫秒）取整。用户态时间是两者之差，内核态时间跨过一个滴答时一下子多出 10 毫秒，总数却只多了一点，用户态时间就少了将近 10 毫秒。线程退出时改用 getrusage 的精确值记进进程，同样可能让用户态时间变少。

- 写了一个边忙边让宿主内核干活（mmap、缺页、sched_yield）的程序，每轮读 times 和 getrusage：tuxport 上跑 6 秒，getrusage 的用户态时间倒退 10–12 次，每次都正好在内核态时间跨过一个滴答的时候；原生上一次也没有。
- Linux 也有同样的问题（内核态、用户态按滴答采样，总数是精确的调度时间），`cputime_adjust` 按采样的比例分配总数，再记下上次报告的值，保证两项各自不倒退。

## 做法

线程记下上次报告的 CPU 时间（`Task::cpu_prev`），按 `cputime_adjust` 的最后一步调整：总数没有增加就沿用上次的；内核态时间不少于上次的；这样算出的用户态时间少于上次时，用户态取上次的，内核态取总数减去它。两项都不倒退，和仍然等于总数。进程的时间是已退出线程的和加上活着的线程的，线程退出时记进进程的值也经过同一个调整，所以进程、`/proc/<pid>/stat`、cgroup 的 `cpu.stat` 也都不倒退。按 Linux 的比例分配没有照搬：宿主记的内核态时间本身已经是按比例分好的。

## 测试

- guest 测试程序 `posix.c` 新增 `test_cpu_times`：边忙边让宿主内核干活，检查 getrusage 和 times 的用户态、内核态时间都不倒退，直到内核态时间跨过几个滴答。

futex_wake05 不是偶发项：已知的偶发失败里记着"[稳定性和内存](12-stability-memory.md)那一轮记为以前就时好时坏，原因没查"。按时间排列所有保存下来的全量结果，它在那一轮之前连续失败 12 次，从那一轮起 60 次全部通过。它检查的是对未映射、`PROT_NONE`、被截短的文件映射的地址做 futex 时返回 EFAULT，正是那一轮修的"`PROT_NONE` 不进页表"和"截短已映射的文件"。从偶发项里去掉，改正了那一篇的记录。
