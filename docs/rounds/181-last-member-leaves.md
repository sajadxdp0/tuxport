# M9 之前：共用翻译的组里最后一个成员离开时作废别人留下的块（2026-11-02）

[上一轮](180-original-dst.md)测试时发现的偶发 SIGILL：跨命名空间的探测脚本里，几个 python3 服务端 import 了 select，客户端没有。最后一个客户端时常在启动后不久崩掉：

```
tuxport: Tier 1: an address space leaves the shared translations of inode 8826 (1 members): an executable mapping differs from theirs
tuxport: undefined instruction 0x00000034 at 0x7fffbedd0214
Illegal instruction
```

第 178 轮的二进制也有（8 次里 3 次），上一轮的 6 次里 4 次。

## 原因

[同一个程序共用翻译](108-shared-translation.md)的组里，成员映射的可信文件映射登记在组里，那里的块所有成员共用。成员在登记过的地址上映射了别的文件时离开组：

- 组里还有别人时，它换用自己的翻译。
- 只剩它自己时，组关掉，它留着原来的翻译，省得把整个程序重新翻译一遍。

第二种情形漏了一点：组里的块不一定都是它翻译的。别的成员退出或者离开之后，它们登记的映射和在那里翻译的块还在组里。最后一个成员离开，正是因为它在某个登记过的地址上映射了别的文件；它留着的翻译里，这段地址上还是别的成员翻译的那个文件的块，它执行到的是别人的代码。

探测脚本里正是这样：服务端 import 的 select 模块登记在组里。客户端 import 的模块少一个，之后加载的模块落在服务端放 select 的地址上。最后一个客户端启动时，接受过三个连接的服务端已经退出，另一个服务端早就离开了组，组里只剩它自己；它映射那个模块时离开组，执行的却是 select 的块，跑到数据上（`0x34`）。

## 做法

最后一个成员离开时，作废组里的实例中与它的映射对不上的块（`check_code_group`，引擎原有的 `tuxport_dbt_retire_outside`）：

- 留下的范围是它的可信映射里与登记一致的那些（`CodeGroup::consistent`：重叠的登记都是同一个版本的同一段文件）。没登记过的映射里本来就没有共用的块。
- 别处共用的块都作废：它在登记过的地址上映射的别的文件，别的成员登记过、它没有映射的地址。
- 带标签的块（成员私有的 JIT 代码）不动，别的成员的标签它查不到。

作废要扫一遍翻译表。每个地址空间只会离开一次，组里从来只有它一个时也一样作废（不会多作废它自己的块，因为都对得上）。

## 测试

- `shared-code` 差分测试组新增 `alone`：父进程独自开组，子进程在一格地址上映射、执行一个文件之后退出，父进程再在同一格映射另一个文件执行。要在三棵独立的进程树里各跑一次：主进程在的时候组里不止它一个，走不到这个情形。两个执行层下都与原生相同；单元测试 `code_groups_register_only_consistent_mappings` 加上 `consistent`。
- 原来的探测脚本（`target/origdst/xall.sh`）跑 8 次都没有崩。

## 推迟项

- [第 108 轮](108-shared-translation.md)记着的另一种：成员野跳到只有别的成员映射过、自己没映射的地址时，执行的是那里的翻译，不是收到 SIGSEGV。还是这样。
- `origdst` 组里各个角色先 import 同一组模块的写法留着（原来是为了避开这个问题），不影响它测的东西。
