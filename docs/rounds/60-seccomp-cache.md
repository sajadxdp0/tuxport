# M9 之前：seccomp 的缓存和快速路径（2026-10-28）

上一轮的 seccomp 每次系统调用都在解释器里运行整条过滤器链，每条指令约 4.5 纳秒；装了过滤器的线程也失去了不持 BKL 的快速路径（§6），连 vDSO 里读时钟这种不检查的调用也要排队等 BKL（[上一轮](59-seccomp.md)的开销）。用 seccomp 做沙箱的多是多线程的程序，每个 futex、每次读时钟都去等 BKL，线程越多越慢。

## 做法

- **按编号缓存**（与 Linux 6.1 的 `seccomp_cache` 相同）：装过滤器时，对 0–511 的每个编号把程序模拟一遍，当作只知道编号和架构（`seccomp::const_allow`，按 `seccomp_is_const_allow`：只认读编号和架构、与常数比较的跳转、无条件跳转、与常数按位与，返回值要正好是 ALLOW）。总是返回 ALLOW 的编号记进位图，再与上一个过滤器的位图按位与，所以新过滤器全放行也放不开旧过滤器拦着的编号。检查时先看链上最新那个过滤器的位图，有这个编号就不运行程序。
  - libseccomp 生成的那种过滤器（先看架构，再一串编号比较）放行的编号都在位图里；看参数的、返回别的动作的编号仍运行整条链。
  - 只是不再运行程序，结果不变，Linux 上也看不出来（只有调试用的 `CONFIG_SECCOMP_CACHE_DEBUG` 才有 `/proc/<pid>/seccomp_cache`）。
- **快速路径**：
  - 线程把位图另存一份原子的（`Task::seccomp_allow`），装过滤器、TSYNC、clone 时由 `seccomp::publish` 更新。有 seccomp 的线程，位图里有的编号照常走不持 BKL 的快速路径。
  - TSYNC 时别的线程可能正在读位图，读到的旧位是同步之前那条链的（新链只会更严），相当于那个系统调用发生在同步之前。
  - vDSO 里读时钟的存根（clock_gettime、clock_getres、gettimeofday）本来就不检查，现在也不离开快速路径：`Fast` 记下 vDSO 的地址（换地址空间的 execve 之后重新记）。Chromium 那样按 clk_id 过滤 clock_gettime 的，编号不在位图里，经由 vDSO 读时钟仍不受影响。

## 结果

单线程、Tier 1，"之前 → 之后"，纳秒/次。过滤器 A 只看架构（6 条），B 再比较 40 个编号（46 条），C 是 B 再按 clk_id 过滤 clock_gettime（clock_gettime 不在位图里）：

| | 没有过滤器 | A | B | C |
|---|---|---|---|---|
| clock_gettime（vDSO） | 87 | 145 → 88 | 143 → 89 | 145 → 89 |
| getppid（持 BKL） | 97 | 110 → 107 | 295 → 102 | 298 → 103 |
| futex 唤醒 | 60 | 125 → 63 | 313 → 60 | 316 → 60 |
| fstatat | 905 | 1220 → 915 | 1440 → 900 | 1445 → 910 |
| pread | 430 | 438 → 442 | 618 → 446 | 628 → 449 |
| 4 个线程同时读时钟 | 350 | 990 → 370 | 910 → 365 | 950 → 382 |
| 4 个线程同时 futex 唤醒 | 365 | 910 → 405 | 1625 → 366 | 1690 → 368 |

装了过滤器之后与没有过滤器时基本一样。4 个线程的那两行是每次调用的墙钟时间，波动较大。

## 测试

- 差分测试 `seccomp` 的快速路径一节新增几个错误的缓存会放过的场景：按参数过滤的 futex，上一个过滤器拦着、新的全放行，快速路径上的系统调用返回 TRAP，按 clk_id 过滤的 clock_gettime。
- 单元测试新增缓存的模拟执行。

## 推迟项

- 缓存只认 Linux 认的写法：先 `TAX`、`ST` 再比较，或者用 `JEQ X` 比较的程序不缓存，每次都运行。
- 位图只到 511 号（tuxport 实现的编号都在里面）。
- 不在位图里的编号仍要持 BKL、在解释器里运行整条链（每条约 4.5 纳秒）。
