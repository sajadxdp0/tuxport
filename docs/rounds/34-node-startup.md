# M9 之前：node 启动（2026-10-26）

前两轮记下的推迟项：`node -e 0` 有大量单条交给 Tier 0 的退出和作废的块。同一个会话里冷启动 0.11 秒、之后每次 0.05 秒，原生 0.02 秒。`--stats` 显示连跑 6 次有 7.9 万次 Tier 0 退出（静态只有 277 条指令）、3.4 万个块作废、3.4 万个块从模板拷贝。

## 做法

### Tier 0 退出（§4.5）

临时记下每次退出的 pc：2.6 万次里 2.3 万次落在 node 里的 4 条指令上，都是 libgcc 的 outline atomics（`__aarch64_ldadd4_acq_rel` 等，GCC 在 arm64 上默认生成对它们的调用）里的 `stxr w15, w17, [x1]`。这些函数先看 `__aarch64_have_lse_atomics`，是 0 就走 LL/SC 循环；Alpine 的 libgcc 不按 HWCAP 设置这个标志，原生运行时也是 0（同一个测试程序在原生 Alpine 里也打印 0）。循环里要写的值在 x17，是 Tier 1 占用的寄存器，比较并交换的循环里没有空闲的寄存器放它，于是整条交给 Tier 0。

- **借一个 guest 寄存器**：取这条指令没用到的一个 guest 寄存器放要写的值，先存进 cpu 结构体里它自己的位置，用完恢复。中间不退出，宿主故障也不从 ucontext 恢复 guest 状态（guard.c 只取 pc），没有人看得到它被借走。

### 作废的块（§4.2 的"翻译保留"）

临时记下每次作废的原因：几乎都来自新地址空间第一次运行时的核对（libcrypto、ICU、libstdc++、libada 等），库在两次运行中映射在同一个地址、内容也一样。原因是核对的时机：这时只有程序和动态链接器映射了，共享库还没加载，块所在的页没有映射，一律算作对不上。

- 实验：页没有映射的块不作废（不安全，只为量上限），10 次热启动 0.50 → 0.43 秒。
- **停放**：落在上一个使用者的文件映射里、页还没映射的块不作废，入口照样改成跳往转发桩，代码和被改写的那条指令留着。分发器查不到某个 pc、它所在的页里有停放的块时，核对这一页里所有停放的块，指令字相同的恢复入口、放回表里，对不上的作废。
  - 第一版逐个恢复，只快了 3%：每个停放的块第一次执行到都要经由转发桩退出一次，6700 次退出把省下的拷贝吃掉了；改成一页一起恢复之后接近上限。
  - 第一版还停放了匿名内存里的块（JVM 的 JIT 代码），Maven 慢了 1.5%：它们下一次多半对不上，停放着只会让查表失败时多拿一次锁。改成只停放文件映射里的（内核层记下的映射从 16 段加到 64 段，node 有二十多个库），并且按页的哈希记停放的块数，查表失败时先不持锁看一眼，没有就不拿锁。

## 结果

- 微基准 `target/mem/atomics.c`（outline atomics 的原子加和比较并交换各一次）：每轮 43 → 8.3 纳秒，原生 7.0。凡是 GCC 编译、用到原子操作的 C/C++ 程序（引用计数、锁）都受益。`node -e 0` 本身几乎没变：这 1.3 万次退出每次只要零点几微秒。
- 6 次 `node -e 0`：翻译的块 8.4 万 → 5.1 万（从模板拷贝的 3.4 万 → 1181），作废的块 3.4 万 → 701，链接退出 11.2 万 → 7.2 万。

| 负载（3 轮交替） | 原生 | HEAD | 之后 |
|---|---|---|---|
| `node -e 0` 冷启动 / 之后连跑 10 次 | 0.07 / 0.20s | 0.11–0.13 / 0.49–0.53s | 0.11–0.12 / 0.44s |
| 原子加和 CAS 的循环，每轮 | 7.0 纳秒 | 43 纳秒 | 8.3 纳秒 |
| python 启动 5 次 | — | 0.63–0.68s | 0.59–0.60s |
| `java -version` 3 次 | — | 0.17–0.20s | 0.16s |
| gcc 编译 `lvm.c` | 0.69s | 2.27–2.30s | 2.22–2.25s |
| `go build`；Maven | 2.2s；1.7s | 6.46–6.47；6.63–6.83s | 6.31–6.33；6.64–6.73s |

之后热启动的样本里翻译后的 guest 代码占 73%（node 51%、musl 14%：动态链接器逐字节比较符号名、libgcc_s 4.5%：解析 DWARF 栈展开信息），DBT 自己 6%，剩下的是宿主内核（缺页、mmap）。这些都是 guest 自己的工作，原生也要做，慢在翻译后代码里每次访存的检查（R1）。

## 测试

- lockstep 的 exclusive 类本来就随机用到被占用的寄存器：同一个种子 200 万个用例里交给 Tier 0 的从 102.6 万降到 80.2 万，全部与硬件一致。
- 差分测试 rewrite 组加上共享库就地改写：用旧库跑过之后换成大小相同的新库，恢复停放的块时要核对出来。

## 推迟项

- 冷启动没有变：第一次要翻译 5 万个块。翻译不跨 tuxport 进程保留（Android 上一个 App 进程里会话一直开着，只有第一次是冷的）。
- 一次全量 cargo test 有一个测试失败，没有看到是哪个，之后连跑 3 次都通过。→ 连跑 40 次抓到是 `procfs_describes_processes` 自己的竞争：`sleep 5 &` 之后马上用 ps 数 sleep 进程，后台的子进程可能还没 exec（comm 还是 sh），Linux 上同样可能。改成先等它 exec 成 sleep，之后单独跑 30 次、全量跑 30 次都通过。
