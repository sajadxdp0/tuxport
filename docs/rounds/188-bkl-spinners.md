# M9 之前：8 核上的扩展性和 BKL 的交接（2026-11-02）

10 月 30 日审性能推迟项时，"地址空间的操作改用每个 mm 自己的锁"（[起进程和 mmap 的持锁时间](109-spawn-mmap-bkl.md)的推迟项，R1 的退路）留着等虚拟机有 8 个核、量过 `-P8` 再定。[测试提速](178-test-speed.md)那一轮把 colima 调到了 8 核，这一轮先在 8 核上量各类并行负载的扩展性，再按结果处理。

## 8 核上的扩展性

原生对照是同一个 gcc 15.2 的 Alpine 容器（`tuxport-difftest` 镜像），tuxport 是这一轮开始时的 release（91300af）：

| 负载 | 原生 | tuxport | 倍数 |
|---|---|---|---|
| Lua 的 33 个 .c，`xargs -P1` / `-P4` / `-P8` | 4.63 / 1.70 / 1.15s | 15.36 / 5.04–5.53 / 3.98–4.04s | 3.3 / 3.0–3.3 / 3.5× |
| `git grep`（Go 的仓库，3 次）1 / 2 / 4 / 8 个线程 | 0.42 / 0.27 / 0.21 / 0.29–0.31s | 0.95 / 0.56 / 0.42 / 0.51s | 2.3 / 2.1 / 2.0 / 1.7× |
| 并行 lstat 的 `git status`，10 次 | 0.12s | 0.12s | 1.0× |
| spawnbench：fork 后 exec `/bin/true`，1 / 4 / 8 个同时，每个每轮 | 152 / 207–217 / 243–253 µs | 155 / 528–541 / 1050–1128 µs | 1.0 / 2.5 / 4.4× |
| spawnbench：`sh -c 'cat \| wc'`，1 / 4 / 8 个同时，每个每轮 | 402 / 624–633 / 836–876 µs | 456 / 1862–1939 / 4114–4217 µs | 1.1 / 3.0 / 4.8× |

- 并行编译到 8 个也和原生一样扩展：`-P8` 比 `-P1` 的倍数只多约 5%。mmap、munmap 拆出 BKL 换不来什么，按 mm 加锁不做。
- 并行读文件（`git grep`、并行 lstat）同样不受 BKL 限制。
- 只有同时起进程不扩展：从 1 个到 8 个，总吞吐一直是每秒约 7 千次，相当于只用一个核。单个进程起进程和原生一样快。
- 第 109 轮记的"4 个同时 exec 376–402 µs"是 4 核的虚拟机上量的。拿那一轮的二进制（`target/mem/bin/tuxport-run-r109c`）在 8 核上交替运行，4 个同时 507–533 µs、8 个同时 1032–1126 µs，与现在的相差不到 4%，不是代码回退。

## 同时起进程时时间花在哪里

perf 剖析 8 个同时 exec（cpu-clock 采样）：内核的 `try_to_wake_up` 本身占 16%，几乎都来自放开 BKL 时的 futex 唤醒；`Shared::lock` 的自旋占约 10%；宿主 `mmap_lock` 的读写信号量争用约 6%。cpu-clock 看不到睡着等锁的时间，所以又加了临时插桩（BKL 的持锁时间、交接的空档、放开之后在 `Bkl::drop` 里做的事，每一轮是一次 fork、exec、退出、等待）：

| | 1 个 | 8 个同时 |
|---|---|---|
| BKL 被占着的时间 | 32% | 65% |
| 每轮持锁 / 拿锁的次数 | 约 52 µs / 27 次 | 约 96 µs / 29 次 |
| 放开之后：放开 mutex（含 futex 唤醒） | 1.1 µs | 49 µs |
| 放开之后：叫醒线程池、触发事件 | 4.9、8.7 µs | 6.5、23 µs |
| 放开之后：交还宿主内存（munmap）、补 fork 的预留段（mmap） | 23.6、5 µs | 85、59 µs |

锁只占了 65%，却平均有 7 个多线程睡着等它。换成自己写的 futex 锁（下面的实验）之后能数清楚：8 个同时的时候，锁 67% 的时间被占着，**另有 30% 的时间空着、同时有线程睡着在等**（被叫醒的线程还没跑起来）；7.4 万次拿锁里睡下 6.2 万次、叫醒 7.1 万次。锁实际上已经饱和，饱和在两件事上：

- **交接**：只让一个线程自旋，它一拿到锁，下一次交接时就没有人在自旋，只能叫醒睡着的。
- **持锁时间变长**：按系统调用分，8 个同时的时候每一样都变慢（µs，括号里是每轮的次数）：

  | | 1 个 | 8 个同时 |
  |---|---|---|
  | clone | 16.3 | 28.7 |
  | execve（3） | 3.8 | 6.3 |
  | exit_group（3） | 2.8 | 4.8 |
  | 写缺页（3） | 1.9 | 2.8 |
  | brk（2）、mmap（1）、mprotect（2） | 0.66、0.64、0.33 | 3.2、2.9、0.9 |
  | rt_sigprocmask（6） | 0.29 | 0.44 |

  没有哪一样特别突出，像是锁在核之间换手、内核的数据总在别的核的缓存里；brk、mmap、mprotect 涨得最多，它们还要和放开 BKL 之后的 munmap、mmap 抢宿主的 `mmap_lock`。

按这些数，8 个同时的时候每轮约 104 µs 持锁、29 次交接各约 1 µs，合起来与实测的每轮约 137 µs（1100 µs ÷ 8）对得上。改交接最多只能省掉后一部分。

## 试过的交接方式

实验版（`TUXPORT_BKL_*` 环境变量选策略，编一次）交替运行 3 轮，spawnbench 各项的中位数（µs）：

| | exec ×1 | ×4 | ×8 | 管道 ×4 | ×8 |
|---|---|---|---|---|---|
| 原来（std 的 Mutex，1 个自旋） | 152–161 | 531–541 | 1105–1152 | 1863–1904 | 4025–4118 |
| 自己的 futex 锁，1 个自旋 | 152–153 | 592–594 | 1371–1372 | 2294–2304 | 5166–5184 |
| 自己的锁，有线程在自旋时放锁不叫醒睡着的 | 156–160 | 595–612 | 1338–1364 | 2317–2339 | 5088–5150 |
| 自己的锁，4 个自旋、不叫醒 | 153–161 | 488–501 | 1081–1113 | 1670–1737 | 3817–3879 |
| 自己的锁，8 个自旋、不叫醒 | 153–165 | 490–502 | 1099–1119 | 1677–1704 | 3843–3885 |
| std 的 Mutex，最多 2 个自旋 | 152–159 | 489–505 | 1049 | 1686–1726 | 3565–3668 |
| **std 的 Mutex，最多 4 个自旋** | 154–162 | **480–483** | **1031–1037** | **1597–1645** | **3519–3591** |

- 自己写的锁（状态字、睡着的和自旋的线程数各一个原子计数）本身就比 std 的慢两成：几个计数和状态字在同一个缓存行上，每次没拿到锁都要多改两三次，这一行在 8 个核之间来回。"有线程在自旋就不叫醒睡着的"省掉了三分之二的 futex 唤醒，墙钟却没有变快。
- 自旋 100 µs 也试过（1 个自旋、不叫醒），与 30 µs 一样。
- std 的 Mutex 不动，只把同时自旋的线程从 1 个放宽到最多 4 个，最快，改动也最小。

## 做法

- **同时最多让宿主 CPU 数一半的等锁线程自旋**（1 到 4 个，`kernel::max_spinners`），原来只让一个。`Shared::spinning` 从标志改成计数：超过上限的直接睡下，自旋的仍然只读"有人持有"的标志、最多 30 µs。8 核上是 4 个，手机的 8 核也是 4 个。

## 结果

与 91300af 交替运行 3 轮：

| 负载 | 之前 | 之后 |
|---|---|---|
| exec 4 / 8 个同时（每个每轮） | 531–541 / 1105–1137 µs | 480–483 / 1031–1037 µs |
| 管道 4 / 8 个同时 | 1863–1902 / 4079–4118 µs | 1597–1645 / 3519–3591 µs |
| exec 16 个同时（线程比核多） | 2348–2435 µs | 2144–2174 µs |
| exec 1 个 | 152–161 µs | 154–162 µs |
| Lua `xargs -P8` | 3.91–4.01s | 3.85–3.94s |
| `go build` 冷编译 | 4.83–4.87s | 4.65–4.72s |
| Maven / Gradle 热构建 | 5.81–6.07s / 1.35–1.42s | 5.73–6.01s / 1.33–1.43s |

多自旋的代价是 CPU（tuxport-run 的用户态加内核态时间，各 2 轮）：8 个同时 exec 再 8 个同时跑管道，墙钟 0.78–0.80 → 0.71–0.73 秒，CPU 2.39–2.43 → 2.84–2.87 秒（+18%）；单个进程起进程、`go build` 两次（32.9–33.1 → 32.6–32.8 秒）、Maven 加 Gradle（70.9 → 70.5 秒）不变。只有锁争得厉害时才多自旋。

8 个同时 exec 仍是原生的 4.2 倍：剩下的是持锁时间本身，见推迟项。

## 测试

- 没有新的测试：锁本身还是 std 的 Mutex，只改了同时自旋的上限；多个线程、多个进程同时取 BKL 的路径原来的测试都覆盖到（guest 测试 `threads.c` 的反复 munmap、差分测试 `c-programs` 的并发读写和 stat、`fork`、`processes`）。
- 最后的 release 与 91300af 再交替 2 轮：exec 4 / 8 个同时 543–547 / 1129–1134 → 495–496 / 1047–1066 µs，管道 1924–1972 / 4140–4173 → 1673–1676 / 3570–3604 µs。
- 只在 colima 的虚拟机里跑，没上手机。

## 推迟项

- 同时起进程仍只用到一个核：8 个同时 exec 是原生的 4.2 倍、跑管道 4.1 倍。要扩展到 8 个核，每轮持锁（8 个同时约 100 µs，单个约 50 µs）要降到每轮时间的八分之一左右，也就是 clone、execve、exit_group、wait4、缺页、brk 这些起进程路上的大部分都不再持 BKL。内核的进程表、地址空间、fd 表、信号状态都是 BKL 下的 `Rc<RefCell<…>>`，这等于重写内核层的核心数据结构；受益的只有短命进程扎堆的负载（`make -j` 里的小命令、并行跑的测试脚本），以编译为主的构建只差约 5%。没做。小一点的做法，比如 rt_sigprocmask 不取 BKL（每轮 29 次拿锁里有 6 次），估计不到一成，没量。→ 试过（M9 之前：rt_sigprocmask 不取 BKL 的尝试和进出分发器的共用计数）：每轮少拿 6 次锁，同时起进程的吞吐不变，没有采用；单线程加协程、类似 epoll 的事件循环、按 fork 家族给地址空间加锁也在那一篇讨论过、量过，都先不做（回来做的条件见那里）；起进程仍持 BKL
- 宿主 `mmap_lock` 的争用（[起进程和 mmap 的持锁时间](109-spawn-mmap-bkl.md)的推迟项）：同时起进程时 brk、mmap 在锁里慢 3–5 倍，放开 BKL 之后的 munmap、mmap 每轮从约 29 µs 涨到约 144 µs。
- 只在虚拟机里量过。虚拟机里的核间中断（futex 唤醒）比真机贵，交接的空档可能被放大；手机的小核上自旋是否划算、多用的 CPU 对耗电的影响都没量（R1）。
